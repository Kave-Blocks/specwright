# 09 — share-dialog

Spec: [`context/feature-specs/09-share-dialog.md`](../feature-specs/09-share-dialog.md)

- `09-share-dialog.md` — project sharing. **Backend:** `lib/collaborators.ts` holds the enrichment layer — `MemberView` (`{id,email,name,imageUrl,role:"owner"|"collaborator"}`), `normalizeEmail()` (trim + lowercase + minimal shape check at the boundary; lowercased because Clerk stores emails lowercased, so stored collaborator rows keep matching the identity email used in `getAccessibleProject`/`getEditorHomeProjects` access checks), and `listProjectMembers({id, ownerId})` which reads `ProjectCollaborator` rows (ordered `createdAt asc`) and, **in parallel**, resolves the owner (Clerk `getUser(ownerId)`) and enriches collaborators (`getUserList({ emailAddress })`, keyed by lowercased email). It returns the **owner first (role `owner`)** then collaborators (role `collaborator`) so the dialog renders one "people with access" list. Name = firstName+lastName → username → `null`; avatar = `imageUrl` only when `hasImage` (Clerk's generated default avatars are treated as "no avatar"); owner email = primary (falling back to first). Enrichment is best-effort: a Clerk failure is caught + logged and members fall back to their identifier (email, or "Project owner"). **API routes:** `app/api/projects/[projectId]/collaborators/route.ts` — `GET` (membership-gated: owner **or** collaborator via the existing `getAccessibleProject`, so a non-member gets `404`) returns `{ members }`; `POST` (owner-only via `verifyProjectOwnership`) invites by email, `400` on invalid email, `409` on `P2002` duplicate, returns the refreshed `{ members }` (`201`). `app/api/projects/[projectId]/collaborators/[collaboratorId]/route.ts` — `DELETE` (owner-only) removes via `deleteMany({ id, projectId })` (project-scoped so a foreign collaborator id can't be removed), `404` when nothing matched, returns refreshed `{ members }`. POST/DELETE build members with `ownerId: userId` (owner-only routes, so the caller is the owner). Both invite + remove enforce ownership server-side per spec. Shared helper `ownershipErrorResponse(403|404)` was hoisted into `lib/projects-api.ts` (and the existing `[projectId]/route.ts` refactored to use it) to avoid duplicating the `403`/`404` JSON shape. `lib/project-access.ts` `getAccessibleProject` now also selects `ownerId` (interface `AccessibleProject` gained `ownerId`) so the page can compute `isOwner = project.ownerId === identity.userId` and the GET route can pass the project straight into `listProjectMembers`. **UI:** `components/editor/share/share-dialog.tsx` is a `"use client"` dialog modeled on the provided reference — an owner-only "Workspace link" card (Copy-link button → `Copied!` for 2s via `navigator.clipboard`), an owner-only mail-icon invite field (raw `<input>` inside a bordered card so the icon sits inside), then a "People with access" header with an "N total" count and the member list. Each row is a bordered card: avatar, name (falling back to email → role label), a role badge on every row (brand `OWNER` pill `border-brand/30 bg-accent-dim text-brand`; muted gray `COLLABORATOR` pill `border-subtle-border text-copy-muted` — a label only, since role editing isn't built yet), email sub-line when a name is present, and a remove (Trash2) button only on collaborator rows when `isOwner`. Collaborators see only the read-only list (no link card, no invite, no remove). The dialog fetches on open and manages its own loading/invite/remove/copy/error state. Avatars render a Clerk `<img>` when available, else an initial in a `bg-subtle` circle (plain `<img>` with a scoped eslint-disable — Clerk avatar hosts aren't configured for `next/image`). `DialogContent` is widened to `sm:max-w-xl`. Wiring: `EditorWorkspace` gained `projectId`/`isOwner` props + an `isShareOpen` state and renders `<ShareDialog>`; `WorkspaceNavbar` gained an `onOpenShare` prop wired to the existing `Share` button; `app/editor/[roomId]/page.tsx` passes `projectId`/`isOwner`. Verified with `tsc --noEmit`, `npm run lint`, `npm run build` (both new routes registered), unauthenticated `GET`/`POST`/`DELETE` → `401` via curl, and a throwaway `tsx` script against the real DB + Clerk: `listProjectMembers` returns owner-first (role `owner`, email resolved) + collaborator (role `collaborator`, email fallback when unmatched), member count correct, cascade delete cleans up. Note: the read-only vs owner UI branch was verified structurally (build/lint/data path), not in a live signed-in browser session.
