# 35 — brief-persistence

- **`35-brief-persistence.md` — complete. The architecture brief is now durable, closing the "not done" item unit 34 recorded against itself.** Five small pieces, exactly as specced. **(1)** `Project.architectureBrief String?` — one nullable column, migration `20260722032747_add_project_architecture_brief` (a bare `ADD COLUMN ... TEXT`, no backfill, so every existing project reads `null` rather than `""`). **Not a new model, deliberately**: this is a *single current value per project*, the same shape as `canvasJsonPath`, overwritten on every Generate — unlike `ProjectSpec`, which is a list of point-in-time artifacts users browse. **(2)** `AccessibleProject` gains the field and `getAccessibleProject`'s `select` selects it, **adding no query at all** — that function is already `cache()`-wrapped from unit 34, so the room layout and Project Home share one lookup and the new field arrives free. **(3)** `PUT /api/projects/[projectId]/brief`, guarded by **`withProjectMember`, not `withProjectOwner`** — the brief is composed collaboratively the same as the canvas, and the canvas route is the direct model for the guard and the overwrite shape. It **writes straight to Postgres with no Blob half**: the artifact is bounded (a composed brief measures ~1.2–4.5k chars by unit 33's own measurement), so it is stored the way `Project.description` is, not the way genuinely-large generated content is. Empty/whitespace body **400s**; over-length **truncates to `MAX_BRIEF_LENGTH = 20_000`, never rejects** — the policy `MAX_FREE_TEXT_LENGTH`, `AI_CHAT_MAX_LENGTH`, and the `MAX_LABEL_LENGTH` fix below all already follow for human-typed text with no `maxlength` at its source: a brief that merely ran long is still a legitimate brief. **No `GET`, on purpose** — a client already has the value via `getAccessibleProject`, and the next unit's server-side consumer reads the column directly through Prisma rather than making an HTTP round trip to its own backend. **(4)** `DiscoveryView` fires the `PUT` **alongside** `send()`, not awaited and not gating it, with failures `console.error`d and swallowed — the best-effort stance `ensureFeed`/`ensureRoom` already take in `lib/liveblocks.ts`, applied here because the record is a durability improvement, not part of the critical path (the status strip, the run) the user is watching. It lives in `DiscoveryView` rather than `useDesignSubmit` because that hook is **shared with Canvas's freeform chat**, and a one-line prompt typed into Canvas is not a brief. **(5)** Home's Architecture Interview card reads **"Brief composed"** when one exists and shows **no line** when none does, derived from `Boolean(project.architectureBrief)` in the page — again no new query, the same `getAccessibleProject` call already backing `hasCanvas`. **One tension inside the spec, resolved toward the mechanic rather than the phrasing, and worth recording because it is observable:** step 4 opens with "on a *successful* Generate" but then requires the write fire "alongside triggering the design run, **not gating it**". Those cannot both hold — gating on success means awaiting the run start. It fires alongside, so **a brief is persisted even when the design run fails to start**. That is the better reading rather than merely the literal one: the card asserts *a brief exists*, not *a run happened*, and the user did compose and submit real work that would otherwise be lost precisely in the failure case where losing it hurts most. **Verified — and the shape of the verification is narrower than `30`–`34`'s, which is the honest caveat.** The persistence layer was driven against the **real database** through a throwaway project row (created and deleted): a never-run project reads **`null`, not `""`**; the exact text **round-trips byte-for-byte**; a re-run **overwrites in place** with the project count still **1** (no history, no second record); a 50k-char submission **truncates to exactly 20,000** rather than 400ing; and a typical brief sits well under the cap — **7/7 pass**, QA row cleaned up. Plus `tsc --noEmit`, `eslint`, and `npm run build` all clean, with `/api/projects/[projectId]/brief` registered in the route table. **No Blob object is created** — trivially confirmed, the new code imports `@vercel/blob` nowhere. **Not exercised, stated plainly:** the route was **not** driven through a real signed-in browser the way `30`–`34` were (no throwaway Clerk user was minted this session), so the HTTP path — guard, 400 branch, and the Discovery→`PUT` call actually firing on a real Generate — is backed by the DB-level checks, the unchanged `withProjectMember` wrapper it reuses, and types, **not by observation**. The "a simulated persistence failure doesn't block the run" check is likewise **structural rather than demonstrated**: the call is un-`await`ed and its own `try/catch` swallows both a rejected `fetch` and a non-`ok` response, so there is no path by which it can reach the Generate flow — but nobody watched it fail. **One caveat carried forward, not introduced here:** `readJsonBody` does `await request.json()`, so the whole body is parsed into memory *before* the 20k truncation runs — the same limitation already recorded against the spec-payload fix below, and mitigated the same way (authenticated, membership-checked, behind a platform body cap). **Not done, per explicit scope limits:** the persisted brief is **not** yet fed into spec generation's prompt (that is the next unit — `trigger/generate-spec.ts`'s prompt builder reading `Project.architectureBrief` as its own labeled section); the interview's per-question answers are **not** rehydrated on reopen (`composeBrief` is one-directional and there is no reverse mapping to `BriefAnswers`); no brief history; no Blob; no `GET`; and no UI anywhere to view or edit a saved brief outside of re-running Discovery.
