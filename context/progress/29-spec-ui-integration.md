# 29 — spec-ui-integration

Spec: [`context/feature-specs/29-spec-ui-integration.md`](../feature-specs/29-spec-ui-integration.md)

- **`29-spec-ui-integration.md` — complete. The Specs tab is real: it lists the project's specs, previews one as rendered Markdown, and downloads it — and the dead "Generate Spec" button now actually generates.** This closes the last gap in the spec feature: `27` built the generation backend and `28` persisted the output, but **nothing in the UI could reach either**, so a spec could neither be produced nor read from the app. **Three gaps in the spec, flagged before implementing; the user chose the resolution for each.** (1) The spec says "fetch specs from the backend using the **existing** ProjectSpec API" — but no such API existed. `28` shipped only the *download* route; there was **no list endpoint**, so "spec list loads for the current project" was unreachable, while the scope limit said "do not implement backend logic". Resolved by adding a **thin read-only list route** (the scope limit reads as "don't rebuild the backend"; the spec's author simply assumed this route existed). (2) The spec says to display a **`filename`**, but `ProjectSpec` has **no filename column** (`id`, `projectId`, `filePath`, `createdAt`), and `filePath` is the private blob URL, which must never reach a client — so the filename is **derived server-side** from the spec id. No schema change. (3) **No Markdown renderer was installed** (no `react-markdown`, no `marked`, no `@tailwindcss/typography`); `react-markdown` was added. A fourth, non-blocking gap was flagged and the user opted to fix it: the **"Generate Spec" button was a dead static button**, so the list would have been permanently empty in practice. **List route (item 1)** new **`app/api/projects/[projectId]/specs/route.ts`** (`GET`) — `withProjectMember` (owner **or** collaborator; the same guard and the same 404-masking as the sibling download route), `findMany` scoped to `project.id` (the id the *guard* resolved, never the raw path param), `orderBy: { createdAt: "desc" }` (served by `28`'s existing `@@index([projectId, createdAt])`). The response is **metadata only**: `{ id, filename, createdAt }`. **`filePath` is never selected into the query at all** — not selected-then-stripped, but never read — so the private blob URL cannot leak through this route by construction. `createdAt` is serialized to an **ISO string**, since a `Date` does not survive JSON. **Preview needs no new endpoint — the one structural insight.** The spec asks to "fetch the spec content through an existing endpoint", and the only one is the **download** route, which answers with `Content-Disposition: attachment`. That header governs a browser **navigation**, not a `fetch`: `fetch(url).then(r => r.text())` reads the Markdown body straight out of the same route. So **one route serves both the preview and the file download**, no Blob is touched from the client, and no backend was needed for item 2. **Shared client types** new **`types/specs.ts`** — `ProjectSpecSummary`, `ProjectSpecListResponse`, and `specDownloadUrl(projectId, specId)`. Deliberately **not** placed in `lib/spec-agent/storage.ts`: that module imports `node:crypto` and `@vercel/blob`, so it is server-only, while these shapes are consumed by a client component. **Spec list (item 1)** new **`hooks/use-project-specs.ts`** — plain `fetch` + `AbortController` (the `useCanvasAutosave` pattern), returning `{ specs, isLoading, error, refresh }`, with a request-id guard so a stale response can't overwrite a newer one. **No global state** (a scope limit): the list is local to the tab. **Preview modal (item 2)** new **`components/editor/ai/spec-preview-dialog.tsx`** — shadcn `Dialog` + `ScrollArea` + `Button`, `rounded-3xl` per `ui-context.md`'s modal scale. Escape, the focus trap, and the close button all come from the Dialog primitive — **nothing keyboard-related is hand-rolled**. The body is a **child that only exists while a spec is selected**, so closing the modal unmounts it and the Markdown is dropped: that is how "do not store spec content in frontend state long-term" is *enforced structurally* rather than merely intended. **Markdown renderer** new **`components/editor/ai/spec-markdown.tsx`** — `react-markdown@10` + **`remark-gfm`**. The GFM plugin is **not cosmetic**: tables and task lists are GitHub extensions, not CommonMark, and a test caught the spec's own `| Layer | Tech |` tables rendering as **literal pipe text inside a `<p>`** without it (the `table`/`th`/`td` components I had styled were never reached). Every element is styled explicitly against the `globals.css` tokens because `@tailwindcss/typography` is not installed and the theme is dark-only. **Raw HTML is not rendered** (no `rehype-raw`, deliberately) — spec content is **LLM-authored**, and a live `<script>` or `onerror=` handler in it would be an injection; verified empirically that hostile markup is escaped to visible text, creating no element and no handler attribute. A third bug the tests caught: react-markdown hands every component its **mdast `node`**, and spreading it onto the element emitted a bogus **`node="[object Object]"`** DOM attribute — now stripped by a `withoutNode` helper (which *deletes from a copy* rather than destructuring an unused binding, since the project's lint rules reject the latter — the repo was warning-clean and stays so). **Download action (item 3)** new **`lib/spec-download.ts`** — builds an `<a download>` and clicks it, so **the browser handles the file**, exactly as the spec asks. It is a same-origin request, so the Clerk session cookie rides along and the route's access check runs normally. Offered on **both** the list item and the modal, per spec. **Generate wiring (beyond `29`'s scope — user-approved)** `SpecsTab` now POSTs `/api/ai/spec` → `/api/ai/spec/token` → tracks the run with `useRealtimeRun<typeof generateSpec>`, then **refreshes the list on completion** (safe because `28` persists the spec *before* the task completes, so the row exists by then). It reuses `26`'s hard-won realtime lessons rather than rediscovering them: **`onComplete` is deliberately not used** (its once-per-mount guard would leave a second generation hung forever), completion is derived from the run status, the hook is **keyed by run id**, and the settle is deferred through a `setTimeout` with the guard claimed *inside* the timer. The status line reads the run's **own metadata** (`27`'s `SpecRunMetadata`), not the shared `ai-status-feed` — a spec is written for the person who asked for it — and the metadata is **validated, not trusted**, since it crosses the network. **Chat history is capped at the last `MAX_CHAT_MESSAGES` (100)**: a long-running room would otherwise blow the payload cap and get a bare 400. An **empty canvas** and an **over-cap graph** are both caught client-side with a real message — silently truncating a graph would produce a spec describing a canvas the user never drew. **Two shared extractions (de-duplication, not new abstractions)** `useRoomReady` moved out of `ai-architect-tab.tsx` into **`hooks/use-room-ready.ts`**, because the Specs tab hits **the exact same trap `26` was bitten by**: it reads the `ai-chat` feed for generation context, and a Liveblocks feed's first page is fetched **over the WebSocket** — a read issued before the socket connects is dropped, times out after 5s, and is cached as a permanent error (`autoRetry: false`). So the Generate button is gated on the room connection while the **list, preview, and download are not** (they are plain HTTP and need no room). The run-completion status set moved into **`lib/trigger-run.ts`** (`isFinishedRunStatus`), now shared by both tabs. **Canvas graph bridge** new **`components/editor/canvas/canvas-graph-context.ts`** — the collaborative nodes/edges only exist inside `CanvasFlow` (`useLiveblocksFlow`), while the sidebar renders outside it, so the graph is bridged out through a **ref**, mirroring `CanvasSaveProvider`'s existing `saveNowRef`. A **ref, not state**, on purpose: the graph changes on every drag, and pushing that through React state would re-render the whole workspace at frame rate. Nothing renders from it — it is read once, at the moment Generate is clicked. A second `useLiveblocksFlow` in the sidebar was rejected as exactly the "parallel realtime state" `architecture-context.md` warns against. **Sidebar and tabs were not redesigned** (a scope limit): the existing layout, `Tabs`, and card treatment are kept; `SpecsTab` just takes a `projectId` now. **Verified — and the tests earned their keep, catching three real bugs (the missing GFM tables, the `node` attribute leak, and a too-naive security assertion of my own).** `tsc --noEmit`, `npm run lint` (**0 errors, 0 warnings** — confirmed the 17 warnings I briefly introduced were all mine, and they are gone), and `npm run build` are all clean, with the new route registered (`ƒ /api/projects/[projectId]/specs`). A **10-check live round-trip against the real Postgres database** (throwaway projects, cleaned up) exercised the list route's exact query + mapping: only the project's own specs are returned, a spec from **another project is excluded**, ordering is **newest-first**, the filename derives as `spec-{id}.md`, `createdAt` survives as an ISO string, an unknown project yields an empty list, and specs cascade away with the project — plus the load-bearing security property, that the response carries **no `filePath` key** and the serialized body **contains no blob URL**. A **13-check render test** of the Markdown component (real spec Markdown → headings, bold, both list types, a **GFM table**, code block, inline code, blockquote, `rel="noopener"` link, tokens-only styling, no `[object Object]` leak) plus a **4-check injection test** proving hostile LLM markup creates **no live element and no live handler attribute** (`onclick="` never appears — only the escaped `onclick=&quot;` inside visible text). Finally, a **live dev-server smoke test**: an unauthenticated `GET` to the new list route returns a clean **`401 {"error":"Unauthorized"}`**, identical to the download route, proving the guard fires before any database work, with no compile errors in the dev log. **Not exercised:** the **authenticated** browser flow — list → preview → download, and a real Generate → Trigger run → list refresh — needs a signed-in Clerk session (the editor is behind the auth wall; this session has no credentials, the same constraint as `10`–`28`) **and** the Trigger.dev dev worker with `OPENAI_API_KEY`/`DATABASE_URL`/`BLOB_READ_WRITE_TOKEN` in the Trigger environment. The data path those flows depend on is the same query, mapping, renderer, and guard the tests above exercised end to end.

### Follow-up — 2026-07-13

- **`29` QA follow-up — two real bugs found by code review and fixed; a third finding reviewed and rejected.** All three came from CodeRabbit against the `29` diff; each was verified against the *installed* package source rather than taken on the reviewer's word, and one of the three did not survive that check. **(1) Fenced code blocks with no language rendered as inline pills** (`components/editor/ai/spec-markdown.tsx`). The `code` component served both inline code and fenced blocks and told them apart with `className?.startsWith("language-")` — but that class is **only set when a fence carries an info string**, confirmed in `mdast-util-to-hast`'s `code` handler (`if (language.length > 0) properties.className = ['language-' + …]`). A bare ` ``` ` fence therefore arrives **indistinguishable from inline code**, and specs are **LLM-authored**, which omit the language tag constantly — so those blocks got the brand-colored pill treatment *inside* the `<pre>`. Reproduced by rendering (`<pre class="PRE-BOX"><code class="INLINE-PILL">npm install</code></pre>`). **Fix — the detection was deleted, not repaired.** CodeRabbit proposed sniffing the children for a trailing `\n`, which does work, but *only* because that same handler happens to do `node.value + '\n'` — it couples the rendering to an undocumented implementation detail of a transitive dep. Instead: `code` **always** renders the inline pill, and `pre` resets its own child back to block styling via `[&>code]:…` utilities. This is sound precisely because **`rehype-raw` is deliberately absent** (`29`'s injection defense), so authored HTML is escaped and **a fenced block is the only thing that can ever produce a `<pre>`** — the reset lands on exactly the blocks and never on inline code. Verified at the CSS level, since the fix rests on specificity: Tailwind v4 emits `.\[\&\>code\]\:bg-transparent > code` at **(0,1,1)** against `.bg-subtle` at **(0,1,0)**, both in the same `@layer utilities` and **neither wrapped in `:where()`** (which would have zeroed it and silently broken the fix), so the reset wins regardless of source order. Note this drops the `language-*` class from the `<code>` — exactly as the previous code did — so it is the line to revisit if syntax highlighting is ever added. **(2) The AI chat feed was capped at one page, silently starving spec generation** (`hooks/use-ai-chat.ts`). `useFeedMessages(AI_CHAT_FEED_ID)` was called with no options. Confirmed in `@liveblocks/core`: the default **`PAGE_SIZE = 50`**, `FeedMessagesAsyncResult` is a `PagedAsyncResult` carrying **`fetchMore`/`hasFetchedAll`/`isFetchingMore`** (none consumed), and — the load-bearing detail — **`limit` is a *page size*, not a cap**: its own type doc reads *"Does **not** cap the length of `messages` — pagination loads additional pages until `hasFetchedAll` is true."* **The concrete defect the reviewer only gestured at:** `specs-tab.tsx:298` does `chatHistory: messages.slice(-MAX_CHAT_MESSAGES)` with **`MAX_CHAT_MESSAGES = 100`** — so the code deliberately contracts spec generation to the last 100 messages while the hook **could never hand it more than 50**. That `slice(-100)` was **dead**, and spec generation was **silently running on half the history it was designed for**, with no failure mode that would ever have surfaced it. **Fix:** `useFeedMessages(AI_CHAT_FEED_ID, { limit: MAX_CHAT_MESSAGES })`. `specs-tab.tsx` (also client-side) already imports that constant from `@/lib/spec-agent/payload`, so this introduces **no new coupling**. The `messages` docstring — which claimed a completeness it never had — now states the bound explicitly. **Left unfixed, deliberately:** scrollback past 100 messages is still unreachable (`fetchMore` is still uncalled, and there is no "load more"). The bound is *correct* for the AI path — pushing unbounded history into an LLM is exactly what the 100-message contract exists to prevent — so what remains is a limit on **human scrollback**, which is a product decision, not a bug. **(3) Rejected: "pin the Trigger CLI to the SDK version"** in `.github/skills/trigger-getting-started/SKILL.md`. The claimed contradiction is a misreading: that guide's own "Common mistakes" entry faults `@latest` **against an old pinned SDK** — the culprit is a *stale SDK*, not `@latest`. `npx trigger.dev@latest` is what **Trigger.dev's own docs prescribe everywhere**, its `dev` command performs a version-mismatch check and prompts first, and this project **already pins `trigger.dev: 4.5.3`** in `devDependencies` with a `trigger:dev` script that runs the *local* binary and never touches `npx` (`npm view trigger.dev version` → `4.5.3`, identical). The file is also **generated** (`.claude/` and `.github/` copies are byte-identical; it says "Re-run the trigger.dev skills installer after upgrading"), so a hand-edit would be clobbered — and hardcoding `4.5.3` into prose would **add a second place to update and rot into a wrong instruction** on the next SDK bump. No change made. **Verified:** `tsc --noEmit` and `eslint` clean on both changed files; the code-block bug reproduced *and* the fix confirmed by rendering real Markdown (bare fence, ` ```ts ` fence, and inline code) through `react-markdown@10` + `remark-gfm`, and the specificity claim checked against the **compiled** Tailwind output rather than reasoned about. **Not exercised:** neither fix was seen in a signed-in browser (the editor is behind the Clerk auth wall — the same constraint as `10`–`29`); and the *newest-first* ordering of Liveblocks feeds is taken from the docs plus the `useInboxNotifications` precedent (the docs pages 404'd and the bundle grep was inconclusive) — it is what makes bug 2 "recent tail kept, old history dropped" rather than the far worse "chat frozen in the past", so it is worth confirming against a real >50-message room if one ever exists.
