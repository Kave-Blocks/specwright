# 26 — ai-chat-functional

Spec: [`context/feature-specs/26-ai-chat-functional.md`](../feature-specs/26-ai-chat-functional.md)

- `26-ai-chat-functional.md` — complete. The AI sidebar is now **functional end to end**: a prompt submits, the design run is tracked live, and AI-driven canvas updates arrive through Liveblocks. **Token delivery (item 1) — the one backend touch.** The spec says to read `{ runId, publicToken }` from the `POST /api/ai/design` response, but the `22` route returned only `{ runId }` (a separate `POST /api/ai/design/token` route minted the token). Rather than a second round-trip, the route now returns `handle.publicAccessToken` — a field the Trigger.dev `RunHandle` **already carries** ("an auto-generated JWT that can be used to access the run", verified in `@trigger.dev/core`'s `RunHandle` type), so this adds **no Trigger.dev logic** (scope limit honored — nothing was written, just an existing field surfaced). `/api/ai/design/token` is left in place for re-issuing a token later (tokens expire after 15 min). The request still sends `{ prompt, roomId, projectId }`: the spec's `{ prompt, roomId }` is a subset, and `projectId` is what the route's access check + `TaskRun` record need. **Run tracking (item 2)** `AiArchitectTab` stores `{ runId, publicToken }` in local `activeRun` state and subscribes with **`useRealtimeRun<typeof designAgent>(activeRun?.runId, { accessToken, enabled, id, skipColumns })`** from `@trigger.dev/react-hooks` (already a dependency at `4.5.3`; `import type { designAgent }` is erased at build, so the task never enters the client bundle but its return type still types `run.output`). `enabled: activeRun !== null` keeps the hook idle — and silent about the absent token — between runs; **`id: activeRun.runId`** keys the hook's internal SWR cache **per run** (the default key is a `useId()`, which is stable per mount, so a finished run's cached `run` object would otherwise still read as `COMPLETED` the moment the next run is set, instantly settling it); `skipColumns: ["payload"]` avoids shipping the prompt back. **`onComplete` is deliberately NOT used**, despite being the obvious API: its `hasCalledOnCompleteRef` guard is a plain `useRef(false)` on the hook instance that is **never reset** (confirmed in `node_modules/@trigger.dev/react-hooks/.../useRealtime.js`), so it fires **at most once per component mount** — a second prompt in the same session would never settle and the input would stay disabled forever. Completion is instead derived from the run itself: a `FINISHED_RUN_STATUSES` set (`COMPLETED`/`CANCELED`/`FAILED`/`CRASHED`/`INTERRUPTED`/`SYSTEM_FAILURE`/`EXPIRED`/`TIMED_OUT`; everything else — queued, executing, reattempting, frozen, delayed — is still in flight) matched against `run.id === activeRun.runId`, plus the hook's `error` (a dropped subscription also ends tracking, so a network blip can't leave the chat permanently locked). On settle it publishes Specwright's closing line and clears `activeRun`. The settle is **deferred through a `setTimeout(…, 0)`** to satisfy `react-hooks/set-state-in-effect` (the rule traces the callback into its `setState`, so an `await` alone doesn't appease it — same deferral the `24` status banner uses), and the once-only guard ref is **claimed inside the timer, not before it**: claiming it in the effect body would let a subsequent realtime update's cleanup cancel the pending timer while the guard already read "settled", hanging the run. **Assistant messages (item 2, final AI message)** `types/tasks.ts` gains `AI_CHAT_ASSISTANT_SENDER = { id: "ghost-ai", name: "Specwright" }` (a feed message records no author, so the AI needs an identity in the payload exactly like a person does; the id matches its presence id in `trigger/design-agent.ts`), and `useAiChat()` gains **`sendAssistantMessage(content)`** — same `ai-chat` feed, `role: "assistant"` (the role `25` reserved and never produced; it is produced now), and no dependency on `useSelf()` since the AI carries its own sender. The completion line prefers the run's own **`run.output.planSummary`** (the LLM's summary from `23`) and falls back to a canned "Done — your architecture is on the canvas." — this reads the *run result*, not the graph, so the "don't fetch final graph data" limit holds. **Only the client that triggered the run holds its `runId`, so only it subscribes and only it publishes the reply** — no duplicate messages across sessions, and every other participant still sees the reply because it lands in the shared feed. **Canvas (item 3) — untouched by design.** No node/edge code runs here: the task's `mutateFlow` writes land in the same Storage `useLiveblocksFlow` reads, so generated nodes/edges (and AI presence/cursor) appear on their own. **Status strip (item 4)** the `24`-era busy bar moved from the top of the tab to a **compact strip directly above the input**, shown **only while a run is active** and rendering the latest `ai-status-feed` line (`aiActivity.status.text`, fallback "Specwright is working…") on `bg-base` with a green accent and a pulsing `animate-ping` dot. Active = `pending || activeRun !== null || aiActivity.isWorking` — the shared-presence term is kept from `24` so a **collaborator's** generation also shows the strip and locks the input. **Errors → the chat feed** (per spec): a failed `POST /api/ai/design` and a failed/untrackable run both publish an assistant message into `ai-chat`, so every participant sees why nothing appeared. The inline `AlertCircle` line now covers only the one error the feed *cannot* carry by definition — the feed write itself failing. **Color — the one deviation worth flagging.** The spec both names an exact hex (user bubbles + submit button = `#62C073`) and says "use existing design tokens from `global.css`, do not introduce new colors" — but `#62C073` was **not** a `globals.css` token. It *was* already a project color: the **Green** entry in the canvas node palette (`NODE_COLORS` in `types/canvas.ts`, documented in `ui-context.md`). It is therefore **promoted to a token** — `--accent-green: #62c073` + `--color-accent-green` in `@theme inline` — rather than hardcoded in the component, which satisfies both halves of the rule (exact specified color, no *new* color, nothing hardcoded outside tokens). `ui-context.md`'s token table + a usage note were updated to match. Bubbles: user (own **and** collaborators' — the role, not the author) = `bg-accent-green` with `text-(--bg-base)` dark text (≈8.9:1 contrast; light text on this green would fail, so the token's note says so); AI = `bg-elevated` + `text-copy-primary` (dark bg, light text). Own messages stay right-aligned and collaborators'/AI's left-aligned, preserving `25`'s collaborative layout. Submit button = `bg-accent-green` (dimmed via the Button base's `disabled:opacity-50`, spinner while running). **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean (all routes registered), plus a 9-assertion unit test of the assistant-message path — the exact payload `sendAssistantMessage` builds round-trips through `parseAiChatFeedMessage`, an over-long LLM summary is **clamped** (not dropped), an empty summary yields no message, and **cross-feed isolation holds in both directions** (an AI chat message parses to `{}` as a status → renders no status line; a status message fails chat validation → renders no bubble). **Not exercised live end-to-end:** the real submit → Trigger run → `useRealtimeRun` → completion-reply round-trip needs a signed-in session (the editor is behind the Clerk auth wall, no creds this session — same constraint as `10`–`25`) **and** the Trigger.dev dev worker running with `OPENAI_API_KEY` + `LIVEBLOCKS_SECRET_KEY` in the Trigger environment. The realtime paths are verified via types/build/lint + the unit test + reading the pinned `@trigger.dev/react-hooks@4.5.3` implementation (not just its docs — that is how the `onComplete` and SWR-cache-key footguns above were found), not via a signed-in browser run.

### Follow-up — 2026-07-13

- **`26` QA follow-up — two live bugs found and fixed** (first real signed-in run of the AI chat, in room `testing-ai-design-nvcikx`). Both were diagnosed against the **live** Liveblocks project (the run itself succeeded: 7 nodes + 6 edges written, 2 `ai-chat` messages and 3 `ai-status-feed` messages persisted server-side), so this is the first end-to-end verification of `22`–`26` — the write path, `useRealtimeRun` tracking, and the assistant completion reply all demonstrably worked. **(1) Chat history never rendered — a Liveblocks feed race, not a permissions or schema problem.** Symptom: the sidebar showed the empty state even though the room's `ai-chat` feed held both messages. Confirmed the data existed via the node client (`getFeedMessages`) **and** that the client read path works via a Node repro that entered the room with the exact session token `/api/liveblocks-auth` mints and called the same WebSocket fetch `useFeedMessages` calls internally (2 messages, 160ms). Root cause, traced through the pinned SDK source: Liveblocks fetches a feed's first page **over the WebSocket** (`ClientMsgCode.FETCH_FEED_MESSAGES`), and `flushNowOrSoon()` **early-returns when the socket status isn't `"connected"`** — the request is left unsent in the buffer and rejects after `FEEDS_TIMEOUT = 5000ms`; the feed's `PaginatedResource` is constructed with **`{ autoRetry: false }`**, so on failure it caches `ASYNC_ERR` and *never* clears the promise → the error is permanent for the lifetime of the client, and the `DerivedSignal` returns the error result early so even realtime-arriving messages stay hidden. The AI sidebar mounts **with the workspace**, before the room connects (the auth endpoint must check Clerk, hit Prisma, `ensureRoom`, and ensure both feeds first — easily >5s on a cold dev load), so its fetch always lost the race; **writes still worked** (they happen later, once connected), which is exactly why the chat looked like it had "no history" rather than an error. The canvas's `useAiStatus` never hit this because it renders inside `ClientSideSuspense`, which only mounts once the room is live. **Reproduced and fixed empirically**: a Node harness that fetches immediately under a slow auth fails with `"Feed messages fetch timeout"` after 5002ms, while fetching after `"connected"` returns both messages in 160ms. **Fix** — `AiArchitectTab` is split: the outer component gates on **`useStatus()`** (from `@liveblocks/react`) and renders a "Connecting to the room…" line until the socket connects; the chat body (`AiArchitectChat`, holding `useAiChat` + `useRealtimeRun` + input state) only mounts once it is live, so the feed fetch always goes out on a connected socket. The gate **latches** (`useRoomReady`) — it never un-mounts on a later `"reconnecting"` blip, which would otherwise discard the user's draft and any run being tracked; the first page is already loaded by then, so there is nothing to re-gate. The latch's `setState` is deferred through a `setTimeout(…, 0)` for `react-hooks/set-state-in-effect`, same as elsewhere. **`useAiChat` now also returns `error`** (previously swallowed) and the tab renders it inline — the swallowing is what made a hard, permanent failure masquerade as an empty conversation; the hook's doc comment now states the must-not-mount-early constraint explicitly. **(2) Edges had no labels — a prompt bug, not a schema or renderer bug.** Verified against the room's real storage (`mutateFlow` read-only): all 6 AI edges were stored as `type=canvasEdge` — the custom edge component that *does* render labels — with `data.label: ""`. So the whole path already supported labels: `plan.ts`'s schema carries `label`, `apply.ts`'s `buildEdge` writes it to `data.label`, and `canvas-edge.tsx` renders it. The model simply never emitted one, because the system prompt listed it as "optional label" and never asked for it. **Fix** — `lib/design-agent/plan.ts`'s system prompt now requires it: the EDGES section says to **ALWAYS** label every edge with a short verb phrase (1-3 words: "routes to", "authenticates", "reads", "queries", "caches", "publishes to", …) because an unlabeled diagram isn't useful, and the OPERATIONS line reads `addEdge: id, source, target, label (always) + optional from/to`. No schema, apply, or canvas change. **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean, plus the two live Node harnesses above (feed round-trip + the race repro). **Not yet re-run live in the browser:** the fixed chat gate and the newly-labeled edges need a signed-in session to confirm visually (no creds this session); the gate is proven at the SDK level by the race harness, and the label fix is a prompt change whose storage/render path is already confirmed working.
