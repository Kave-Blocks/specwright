# 23 — design-agent-logic

Spec: [`context/feature-specs/23-design-agent-logic.md`](../feature-specs/23-design-agent-logic.md)

- `23-design-agent-logic.md` — complete. Implemented the full AI design agent: a user prompt in the AI Architect sidebar triggers a durable Trigger.dev task that interprets the prompt with an LLM and writes nodes/edges into the shared Liveblocks room in real time, with visible AI presence and a shared status feed. **Provider deviation (user override):** the spec's Implementation says "use Gemini (`@ai-sdk/google`)", but `GOOGLE_AI_API_KEY` was **never actually in `.env.local`** (only `OPENAI_API_KEY` was), and mid-implementation the user edited the spec's Dependencies line to `OPENAI_API_KEY` and instructed "use openai because we don't have gemini key". So the agent uses **OpenAI** — installed `@ai-sdk/openai@4.0.11` to match the existing provider train (`@ai-sdk/google@4.0.11` / `ai@7.0.19` / `@ai-sdk/provider@4.0.3`); `@ai-sdk/google` is left in `package.json` (now unused, harmless). Model `gpt-4o-mini` via `createOpenAI({ apiKey: process.env.OPENAI_API_KEY })`. **Server-side collaborative flow (the key mechanism):** the task mutates the room through **`mutateFlow` from `@liveblocks/react-flow/node`** — the server-side mirror of the client's `useLiveblocksFlow`. It writes to the exact same Storage (`DEFAULT_STORAGE_KEY = "flow"` → `LiveObject{ nodes: LiveMap, edges: LiveMap }`) using the same `toLiveblocksInternalNode`/`reconcile` serialization, so generated nodes/edges stream into every connected client's canvas live. Its `client` is the existing cached `@liveblocks/node` client (`getLiveblocks()` from `lib/liveblocks.ts`). This **uses** the collaborative flow utility rather than bypassing it (scope limit honored); no canvas architecture change, no new state system. Operations map directly onto `mutateFlow`: add/upsert node, `updateNode({position})` / `updateNodeData`, `removeNode` (+ cascade its edges), `addEdge`, `removeEdge`. **`lib/design-agent/plan.ts`** — the LLM call: `generateObject` (from `ai`) with a `jsonSchema()` schema (zod is not installed) producing a validated `DesignPlan` = `{ summary, operations[] }`. Operations are a deliberately **flat object** (not a discriminated union) with an `op` enum + optional fields, so they map onto a provider structured-output schema; only `op`+`id` are schema-required (per-op fields validated at apply time). **Strict JSON-schema is disabled** via `providerOptions.openai.strictJsonSchema:false` — the OpenAI Responses API defaults `strictJsonSchema` to `true`, which rejects a schema with optional properties (strict mode requires every key in `required`), so it is turned off and correctness is enforced by the defensive apply layer instead. The palette/shapes are **reused from `types/canvas.ts`** (`NODE_COLORS`/`NODE_SHAPES`) → single source of truth; `resolveColor`/`resolveShape` coerce any model output to an allowed pair/shape. The system prompt encodes the 6 shapes' semantics (rectangle=component, pill=service, cylinder=DB, diamond=decision, circle=event, hexagon=external/boundary), the 8 palette names, and left-to-right layered layout rules (columns ~280 / rows ~160, matching the starter templates from `18`); the user prompt embeds a compact JSON of the **current** canvas so the model can extend/refine an existing diagram, not only start fresh. **Server-safe import:** pulling `types/canvas.ts` into the Node task only drags `MarkerType` (a plain enum from `@xyflow/system`); `@xyflow/react` has `sideEffects:["*.css"]` so its React is tree-shaken, and it is SSR-safe regardless (all `window`/`document` access is `typeof window === "undefined"`-guarded). **`lib/design-agent/apply.ts`** — `applyDesignPlan(flow, plan)` applies ops in order with defensive validation: coerces shape/color, **skips dangling edges** (source/target must resolve via `flow.getNode`, which reflects same-plan adds since ops apply sequentially), skips updates/deletes of unknown ids, `deleteNode` **cascades** removal of attached edges (mirrors the client `use-canvas-delete-keys` hook), applies per-shape default sizes + a min-resize floor, and **auto-grids** nodes whose coords are missing/non-finite. Returns an `AppliedSummary` tally used for logging + the completion status line. **AI presence + status feed (all Liveblocks):** (1) **presence** via `liveblocks.setPresence(roomId, { userId:"ghost-ai", data:{cursor,thinking}, userInfo:{name:"Specwright", avatar:"", color:"#6457f9"}, ttl })` — the node client's purpose-built ephemeral presence ("showing an AI agent's presence in a room"). It shows up in every client's `useOthers()`, so the existing `PresenceAvatars` (avatar) and `LiveCursors` (cursor) render the AI automatically with **zero new presence system**; set `{cursor,thinking:true}` at start, refreshed (TTL 180s) before the slow model call, and **cleared** on finish via `{cursor:null,thinking:false}` at a short TTL (3s) in a `finally` so it goes on success *and* failure (and self-expires if the worker dies). (2) **status feed** via `liveblocks.broadcastEvent(roomId, { type:"ai-status", phase, message })` at start/processing/complete/error — this required extending the previously-empty `RoomEvent` type in `liveblocks.config.ts` (the node client's `broadcastEvent` message type resolves to the global `RoomEvent` via `DE`, so `Record<string,never>` would reject the event). New `components/editor/canvas/ai-status-feed.tsx` (rendered inside `CanvasFlow`, inside the room) listens via `useEventListener` and shows a top-center banner to **all** participants (phase-styled Sparkles/spinner/Check/Alert), auto-dismissing terminal states after 4s. (3) **thinking visibility**: `LiveCursors` now passes `other.presence.thinking` to `Cursor`, which renders a pulsing dot + "is thinking…" in the badge (human cursors are always `thinking:false`, so unaffected). **Error handling:** the run is wrapped try/catch/finally — catch broadcasts an "error" status (best-effort, never masking the original error) then rethrows so Trigger retries transient failures (`maxAttempts` 3); a missing `OPENAI_API_KEY` throws `AbortTaskRunError` (config error → no retry); finally always clears AI presence. **Frontend prompt wiring:** `AiArchitectTab` now takes a `projectId` prop and its `send()` POSTs `{prompt, roomId:projectId, projectId}` to the existing `/api/ai/design` route (from `22`, which triggers the task + records the `TaskRun`), appends an acknowledgement bubble on `201` / an error bubble on failure, and blocks re-submit while a request is pending; `projectId` is threaded `EditorWorkspace → AiSidebar → AiArchitectTab`. The `22` route/token/`TaskRun` wiring is untouched. **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean (both `/api/ai/design` routes still registered), plus an 18-assertion unit test of `applyDesignPlan` against a mock `MutableFlow` (fresh generation: shape/color coercion, dangling-edge skip, auto-placement, edge marker/handles/label; and extend/edit: relabel/recolor, move-skip on NaN, unknown-id skip, `deleteNode` cascading its edge, summary tallies) — all pass. Confirmed structurally that `@liveblocks/react-flow/node` is a real exported subpath pulling only `@liveblocks/core` (no React) and that server `mutateFlow` targets the same `"flow"` Storage the client reads; `OPENAI_API_KEY` (real `sk-` key), `LIVEBLOCKS_SECRET_KEY`, and `TRIGGER_*` are all present in `.env.local`. **Not exercised live end-to-end:** the real trigger → OpenAI → `mutateFlow` → client-render round-trip was not run — it needs the Trigger.dev dev worker running with `OPENAI_API_KEY` + `LIVEBLOCKS_SECRET_KEY` synced into the **Trigger.dev environment** (task env comes from Trigger's env store, not automatically from Next's `.env.local`), and the editor is behind the Clerk auth wall with no sign-in creds this session — same constraint as `10`–`22`. The generation/presence/feed paths are verified via types/build/lint + the unit test + tracing against the pinned `@liveblocks/{node,react-flow}` + `ai`/`@ai-sdk/openai` APIs. **Hardening (post-review):** a CodeRabbit finding claimed `applyDesignPlan`'s per-op `flow.*` calls could throw (duplicate edge id / node id collision) and leave a partially-applied plan persisted, and asked for a per-op try/catch. **Investigated and rejected** — traced into `@liveblocks/react-flow/dist/node.js`: `addNode`/`addEdge` are `upsertNode`/`upsertEdge` (`LiveMap.set` when absent, else `existing.reconcile(...)`), so a duplicate id is an **upsert, not an error** (which is the documented intent of the apply layer); `updateNode`/`updateNodeData` early-return on an unresolved id; `removeNode`/`removeEdge` are `LiveMap.delete` (no-op on a missing key). There are **zero `throw` statements** in that package's mutation path (only unreachable internal invariant errors in `LiveMap` about detached/unpooled trees). The partial-persistence harm also doesn't hold: `@liveblocks/node`'s `mutateStorage` buffers ops and force-flushes them, and since `applyDesignPlan` is fully synchronous the whole plan dispatches in one tick and ships as a **single `UPDATE_STORAGE` message**, with the callback rejection path calling `abort()` on that request's signal. A per-op try/catch would guard nothing reachable and would downgrade a genuine Liveblocks invariant error into a silent `summary.skipped++`, so it was **not** added. What *was* added: the one real hole — model output is not runtime-validated (`jsonSchema()` has no `validate` fn and `strictJsonSchema` is off), so a malformed `operations` (non-array/absent) used to blow up as a cryptic `TypeError: not iterable`. `applyDesignPlan` now guards with `Array.isArray(plan?.operations)` and throws `"Design plan is missing a valid \`operations\` array"` **before any mutation** (so still no partial state; Trigger retries and regenerates — ops are id-keyed upserts, so a retry converges). Verified: `tsc --noEmit` + `eslint` clean, plus an 8-assertion check against a mock `MutableFlow` (4 malformed-`operations` shapes → clear throw; a well-formed plan still applies with correct added/skipped tallies; an empty `operations: []` is valid and does **not** throw).
