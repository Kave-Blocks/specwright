# 28 — spec-persistence-download

Spec: [`context/feature-specs/28-spec-persistence-download.md`](../feature-specs/28-spec-persistence-download.md)

- **`28-spec-persistence-download.md` — complete. Generated specs are now persisted (Vercel Blob for the Markdown, Prisma for the metadata) and retrievable through a secure download route.** This closes the loop `27` deliberately left open: the spec-generation task produced Markdown and *nothing stored it*. **Model (item 1)** new **`prisma/models/project-spec.prisma`** — `ProjectSpec { id, projectId, filePath, createdAt }`, exactly the four fields the spec names, plus the `Project` relation (`onDelete: Cascade`, so deleting a project takes its specs' metadata with it) and a `@@index([projectId, createdAt])` for the newest-first listing a future UI will want. `Project` gains the `specs ProjectSpec[]` back-relation (Prisma requires both sides). Migration `20260712111334_add_project_spec` was generated **and applied to the real database** via `prisma migrate dev`. **Metadata only** — `filePath` holds the *blob URL*, never the Markdown, per the spec's "do not store spec content in Prisma". **Storage helper (item 2)** new **`lib/spec-agent/storage.ts`** — `specBlobPath(projectId, specId)` → **`specs/{projectId}/{specId}.md`** (the path `architecture-context.md` already specified), `specDownloadFilename`, and `saveProjectSpec({ projectId, markdown })` which uploads then records. Two deliberate ordering/uniqueness choices: (a) the **id is minted up front** with `randomUUID()` rather than left to Prisma's `@default(cuid())`, because the blob path embeds it — one id names both the object and the row (Prisma accepts an explicit `id` over the default); (b) the **upload happens before the row is written**, so a `ProjectSpec` never points at an artifact that doesn't exist — the reverse order could leave a dangling row, whereas a failure between the two leaves only an inert, unreferenced blob. Unlike the canvas — which **overwrites** one object per project (`addRandomSuffix: false, allowOverwrite: true`) to keep `canvasJsonPath` stable — each spec is a **distinct artifact**, so `allowOverwrite` is left off: a (practically impossible) id collision fails loudly instead of silently replacing an existing spec. Blobs are written **`access: "private"`** with `contentType: "text/markdown"`, matching the canvas pattern. **Where persistence runs — the one structural decision.** The spec says "after a spec is generated" without saying where, and its scope limits forbid frontend/UI logic. That rules out a client-called save route (nothing would call it, leaving the feature dead), so persistence lives **inside `trigger/generate-spec.ts`**, after `generateSpecMarkdown` and before it returns. It is the only place that runs once a spec exists **without a client having to stay on the page** — a spec is now stored even if the requester closes the tab mid-run. This **supersedes `architecture-context.md`'s previous claim** that persisting the spec "is a separate concern" (written under `27`'s scope limits); that file's Spec Generation section was updated, and a new **Spec Retrieval** section added, per AGENTS.md's "update the relevant file if implementation changes the architecture". The task's **output contract is unchanged** — still plain Markdown (`27`'s documented contract), so storage is purely a side effect and a subscriber can still render the spec straight from the run. **One additive surface:** `SpecRunMetadata` gains **`specId?: string`**, published via `metadata.set("specId", …)` once the row exists. Without it the download route would be **unreachable** — the id is otherwise only discoverable by querying the DB, and the spec forbids frontend work that could list specs. The run metadata is the channel this task already uses for status, and only the run's owner holds a token for it. The **blob URL is deliberately not published** there: it is a private artifact reference and must only ever be dereferenced behind the route's access check ("do not expose Blob URLs without access checks"). The task also reports a `processing` phase ("saving your technical spec…") between generation and completion. **Download route (item 3)** new **`app/api/projects/[projectId]/specs/[specId]/download/route.ts`** (`GET`) — wrapped in the **existing `withProjectMember`** guard ("reuse existing project access patterns"), which authenticates the caller and resolves `projectId` to a project they can open as **owner or collaborator** — the same membership that grants access to the canvas the spec was written from, and the same check `POST /api/ai/spec` uses to *generate* one. Then the spec is looked up **scoped to both ids** (`findFirst({ where: { id: specId, projectId } })`) — that is the "verify the spec belongs to that project" check, and it means a spec id from someone else's project cannot be read through a project the caller *is* a member of. Only then is the blob dereferenced (`get(filePath, { access: "private", useCache: false })` — a private blob URL is not publicly fetchable; the SDK attaches the auth token) and its `ReadableStream` handed straight to `NextResponse` — **streamed, not buffered** — with `Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="spec-{specId}.md"` (the filename derives from a server-generated uuid, so it cannot inject header syntax), and `Cache-Control: private, no-store`. **Status codes — one thing worth flagging:** the spec asks to "handle not found and forbidden cases properly", but `withProjectMember` **masks forbidden as 404** (missing project and no-access collapse to the same response so a non-member cannot probe which projects exist) — a deliberate, already-documented convention in `lib/api-auth.ts` and `lib/project-access.ts`, and reusing it is exactly what the spec's own "reuse existing project access patterns" note requires. So: **401** unauthenticated, **404** for no-access / unknown project / unknown spec / spec-in-another-project / artifact missing. The 403-yielding `withProjectOwner` was **not** used, since collaborators may read the canvas and therefore the spec generated from it. **Trigger build config** `trigger.config.ts` gains **`prismaExtension({ mode: "modern" })`** — the task bundle now contains Prisma. "modern" is the correct mode for this project's setup (Prisma **7** + `provider = "prisma-client"` + the `@prisma/adapter-pg` driver adapter, per the extension's own version matrix); it keeps `@prisma/client` external, which the generated client in `app/generated/prisma` imports (`@prisma/client/runtime/client`). Modern mode **does not run `prisma generate` for you** — but `app/generated/prisma` is **gitignored**, so a deploy must run `prisma generate` first. That is a **pre-existing project condition, not a regression**: the Next.js build already depends on it identically. **Deployment note (not code):** the `generate-spec` task now needs **`DATABASE_URL`** and **`BLOB_READ_WRITE_TOKEN`** in the **Trigger.dev environment** (task env comes from Trigger's env store, not Next's `.env.local`) — previously it only needed `OPENAI_API_KEY`. **Verified — and this one *was* exercised for real, unlike `22`–`27`.** `tsc --noEmit`, `npm run lint`, and `npm run build` are all clean, with the new route registered as a dynamic function route (`ƒ /api/projects/[projectId]/specs/[specId]/download`). Beyond that, a **14-check live round-trip against the real Postgres database and the real Vercel Blob store** (throwaway project, cleaned up afterwards — spec row, project row, and blob all deleted) confirmed: the `ProjectSpec` row persists, links to the right project, and stores the blob **URL** (not content) with a `createdAt`; the object lands at exactly `specs/{projectId}/{specId}.md`; the Markdown **round-trips byte-for-byte** and is stored as `text/markdown`; **a plain unauthenticated `fetch` of the blob URL fails** (proving the store really is private and the URL is not a capability); the route's scoping query resolves the spec under its own project and **returns nothing under a different one**; and the row **cascades away** when the project is deleted. Finally, an unauthenticated `GET` to the live download route returned a clean **`401 {"error":"Unauthorized"}`**, identical to the existing canvas route — proving the guard fires before any database or blob work. **Not exercised:** the **authenticated** download (200 + attachment headers in a browser) needs a signed-in Clerk session, which this session has no credentials for — the same wall as `10`–`27`; and the **full generate → persist** path through a real Trigger run needs the dev worker with `OPENAI_API_KEY`/`DATABASE_URL`/`BLOB_READ_WRITE_TOKEN` in the Trigger environment. The persistence code those two paths depend on is the same `saveProjectSpec` + blob-read that the live round-trip above exercised end to end. `trigger deploy` was not run, so `prismaExtension`'s effect on the deployed bundle is verified against the extension's typed options and docs, not a deploy.
