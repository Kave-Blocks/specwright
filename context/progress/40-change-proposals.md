# 40 — Change Proposals

A member describes a change in plain English against a project that already has a spec, and Specwright returns a **proposal**: what shifts in the architecture, which existing build units the change makes stale, and what new work it implies. The proposal applies nothing — accepting a proposal is unit 41.

## What Shipped

### Schema and Migration

`prisma/models/project.prisma` (edit): Added `nextChangeSequence Int @default(1)` and the `changes ProjectChange[]` back-relation. This is the third counter on `Project`, after `nextBuildUnitSequence` (unit 38) and `nextSpecVersion` (unit 39), deliberately the same pattern a third time rather than three patterns, for the identical concurrency reason unit 38 already documented.

`prisma/models/project-change.prisma` (new): `ProjectChange` with id (cuid), projectId, sequence (Int), request (String — the member's own words), status, baseSpecId, proposalPath (String optional — the blob URL), authorId (Clerk user id), and timestamps. `ChangeStatus` enum with PROPOSED/APPLIED/DISCARDED (all three members defined now, not deferred, since an enum member is vocabulary not an anticipated relationship; unit 41 implements the APPLIED transition). `baseSpecId` relates to `ProjectSpec` with `onDelete: Restrict` — deleting a spec a change was reasoned against is refused outright, because a delta without its base cannot be judged. `ProjectChangeImpact` with id, changeId, buildUnitId, reason (String), and `@@unique([changeId, buildUnitId])`. Impact rows reference a unit by `buildUnitId`, never by `key` — unit 38 re-derives a unit's key when its title changes, so key is not stable. Relations cascade: `ProjectChangeImpact` cascades from both `ProjectChange` and `ProjectBuildUnit`.

Migration `20260731160000_add_project_changes` (new): Purely additive (new enum, two tables, one defaulted column), no backfill, applied with `prisma migrate deploy`. `migrate diff` reported an empty migration. **Worth recording:** the first attempt failed because the migration file was generated by redirecting `prisma migrate diff` stdout to the file, which captured dotenv's `◇ injected env` banner as the first line and produced a syntax error. The run was marked `--rolled-back` and regenerated with the `-o` output flag, which writes SQL only — that is the flag to use.

### Server Library

`lib/changes.ts` (new): The one place `ChangeStatus` is translated to/from the lowercase wire vocabulary.

`lib/change-agent/payload.ts` (new): Request schema with `projectId` deliberately absent (room id is the project, access resolved server-side). `request` bounded by **truncation, not rejection**. Proposal schema with `summary`, `architectureDelta` array of `{ kind: "added" | "modified" | "removed", component, detail }`, `affectedUnits` array of `{ key, reason }`, `proposedUnits` array of `{ title, summary }`, and `openQuestions` array. Array caps as runaway guards.

`lib/change-agent/propose.ts` (new): Uses **`generateObject`**, not `generateText` — a proposal must be acted on by unit 41 and so must arrive validated. Its own `CHANGE_MODEL`, never `SPEC_MODEL`, because reasoning over an existing spec plus live units is harder than prose. Input: the change request, current spec's Markdown, the project's `architectureBrief`, canvas graph, and build units as `key` + title + summary + status — all read server-side from access-checked `projectId`, never from request body. System prompt directs the model to express the architecture delta as a delta (added/modified/removed) and to reference existing units by `key` values it was given, with a plain statement that it must not invent a key. Throws when the model returns nothing usable.

`lib/change-agent/validate.ts` (new): Resolves every `affectedUnits[].key` against the project's actual units. A key that does not resolve is **dropped, never stored** — model output is unknown external input and must be validated before it is trusted. Returns both the resolved impact rows (as unit ids) and a count of dropped entries so the run can log it. Normalizes proposed unit titles and summaries (trim, drop empty titles, truncate over-length text).

`lib/change-agent/storage.ts` (new): Uploads the validated proposal document as JSON to Vercel Blob at `changes/{projectId}/{changeId}.json`, mirroring the specs path. Mints the change id up front so one id names both the object and the row. Writes the `ProjectChange` row and its `ProjectChangeImpact` rows in **one transaction** after the upload succeeds, so a failed upload leaves no orphan row. Sequence comes from incrementing `Project.nextChangeSequence` inside that transaction.

`trigger/propose-change.ts` (new): A `schemaTask` validated by the payload schema. Publishes progress on the **run's own metadata**, not on `ai-status-feed` (a proposal mutates nothing shared), reusing `AiStatusPhase` vocabulary. Publishes the resulting `changeId` on metadata once stored — never the blob URL. Reuses `lib/ai-errors.ts` for quota classification and `isTerminalFailure` gating, exactly as `generate-spec` does — a third AI task must adopt unit 37's classification rather than reinvent it.

### HTTP Routes

`POST /api/ai/change` (new): Validates body, resolves project access from authenticated user + `roomId`, then triggers the task and records a `TaskRun`, following `POST /api/ai/spec`. **Refuses with 409 before spending a model call when the project has no spec**, with a message "This project has no specification yet. Generate a spec first — a change is a delta against one." The existing spec run-token route was reused unchanged — it verifies against `TaskRun.runId`/`userId` and never inspects the task, so it needed no generalising.

`GET /api/projects/[projectId]/changes` (new): Lists the project's changes newest-first, metadata only, joining each change's `baseSpec.version` so the client shows what it was reasoned against. `withProjectMember` guard; query by guard-resolved `project.id`, never the raw path param.

`GET /api/projects/[projectId]/changes/[changeId]` (new): Returns the change plus its stored proposal document, dereferencing the blob behind the access check. `DELETE` discards by setting status to DISCARDED and **keeps the row** — a proposal someone considered and rejected is a decision worth keeping. Both scope to `{ id: changeId, projectId }` and answer 404 when nothing matched.

### Wire Types

`types/changes.ts` (new): String-union types for change status using lowercase vocabulary on the wire (`"proposed"`, `"applied"`, `"discarded"`). `ChangeSummary` with id, sequence, request, status, baseSpecVersion, createdAt — **`baseSpecId` and `proposalPath` deliberately absent**, one is a server-side matching detail and the other a private blob URL. `ChangeProposal` shape the client renders: summary, architectureDelta, affectedUnits, proposedUnits, openQuestions. Ordered display metadata for status vocabulary. Module imports nothing from `lib/` or Prisma client.

`hooks/use-project-changes.ts` (new): Mirrored on `hooks/use-project-specs.ts` — plain `fetch` with `AbortController`, reload key, request counter that ignores superseded responses. Exposes `changes` / `isLoading` / `error` / `refresh` / `propose` / `discard`. Mutation failures travel in the result, never in the list's `error`, which lets the no-spec refusal show beside the request box while the list stays on screen.

### Design Decisions Worth Recording

- **Delta kinds are not color-coded.** The obvious encoding is a green/red diff palette; this palette has no such pair, and `text-error` means *something went wrong*, which a deliberate removal did not. Kinds are separated by wording and grouping instead, using the muted badge treatment unit 38 established.
- **Status filter row added to the Changes view.** The spec's UI Details require chips with a *selected* state, and nothing else on this surface sets a status, so a filter is the only honest home for that treatment.

### Real Bug Found and Fixed During QA

Browser QA found the project title **overlapping the "Home" mode-switcher link at 768px**. Two attempts:

1. **First fix was wrong.** `min-w-0` was added to the title `<p>` on the theory that a flex item's default `min-width: auto` was defeating `truncate`. Re-tested, the overlap was unchanged — and *worse* with a longer project name (101px of overlap vs 45px).

2. **Actual root cause:** the title's grid item carried `justify-self-start`, which opts a grid item out of the default `stretch` so it sizes to its **content** rather than to its track. The block therefore grew straight past its `minmax(0,1fr)` track and painted over the switcher, and `min-w-0`/`truncate` were inert because nothing was constraining the box at all. Removing `justify-self-start` fixed it.

**Measured proof after the fix:** at 768px on a short name the title container's right edge is 135 and the nav's left edge is 135 (touching, not overlapping) with the title ellipsing to "40 cha…"; at 768px on the longer name ("40 changes QA (no spec)") right edge 142 vs nav left edge 142, ellipsing to "40 chan…"; at 900px, 201 vs 201 with the full title shown. The fix generalises, which the first one did not.

## Verification Actually Run

- **`npm run build` and `npm run lint`** — both clean, re-run after every change including the navbar fix and doc updates.

- **`npm run verify:changes -- all`** — **44/44 checks passed** against the real Postgres and Blob store:
  - **sequence**: changes take 1/2/3, counter one ahead, no save hands back a blob URL.
  - **concurrent**: 5 parallel `saveProjectChange` calls take 5 distinct contiguous numbers, none failing.
  - **build-units-untouched** (the scope limit that matters most): after a proposal naming existing units, every build unit is **byte-identical including `updatedAt`**, no proposed unit was created as a build unit, `nextBuildUnitSequence` is untouched, no second `ProjectSpec` row written.
  - **impacts**: one row per affected unit referencing by id; renaming a unit leaves its impact row intact; deleting a referenced unit cascades only that impact away and leaves the change readable; stored document holds `buildUnitId` never a title.
  - **discard**: status becomes DISCARDED while row, request text, sequence, `proposalPath`, impact rows all survive; document still readable.
  - **base-spec-restrict**: deleting the base spec is refused, spec still present.
  - **cascade**: deleting a project removes its changes and impacts.
  - **validate**: model-invented unit key is dropped, duplicate reference is dropped, nothing invented reaches the document, drops are counted.

- **Browser QA across three rounds** (real Chromium, signed-in Clerk session, dev server plus Trigger dev worker, against seeded throwaway projects since deleted). Confirmed passing:
  - Changes route rendering and an expanded proposal showing summary, delta grouped by kind, affected units by title, proposed units and open questions.
  - **409 no-spec refusal** with message "This project has no specification yet. Generate a spec first — a change is a delta against one." and no run started.
  - **Cross-project 404** (a change id from another project unreachable through a project the caller does belong to).
  - Discard leaving the row with status Discarded and returning 200.
  - Six-entry switcher present and un-clipped with Share never overlapped.
  - Home grid with Changes fifth and placeholder sixth.
  - **No response body containing `proposalPath`, `baseSpecId`, or a blob URL** (both list and detail bodies were captured verbatim).

- **Model-dependent checks now verified** (the OpenAI key works per Job 1's correction). A real run against a project with a spec and two units ("Auth service", "Billing service"), given "Add end-to-end encryption to all billing records, and require re-authentication before any refund.", returned a proposal whose architecture delta named both real components by name, whose affected units referenced exactly the project's two real unit titles and nothing invented, with two coherent proposed units, and the row showing "Reasoned against spec version 1" / `baseSpecVersion: 1`. Run time ranged 10–40s; in-flight status line read "Specwright is reading your spec…".

## Not Verified — Be Explicit

- **A hallucinated unit key being dropped in a *real* run.** The dropping logic is proven with hand-written input in the `validate` phase, but a real model cannot be made to invent a key on demand, so the path from a genuine model hallucination to a dropped entry has not been observed end-to-end.
- **The spent-quota path** ("a spent quota fails on the first attempt with the quota message, not 'Please try again'"). Testing requires actually exhausting the quota. The classification is unit 37's, reused unchanged.
- **The proposal-run failure UI.** No run failed in QA — every one succeeded — so the terminal error presentation was never observed live.
- **The collaborator path** — inherited from unit 38's open gap; needs a second Clerk account.
- **Concurrency at the HTTP layer** — proven by calling `saveProjectChange` directly, not through concurrent requests to the route.
- One cosmetic network observation, not diagnosed: a `net::ERR_ABORTED` on the change-detail fetch immediately followed by a 200 for the same URL, consistent with a superseded fetch during a React re-render.
