# 30 — canvas-tool-modes

Spec: [`context/feature-specs/30-canvas-tool-modes.md`](../feature-specs/30-canvas-tool-modes.md)

- **`30-canvas-tool-modes.md` — complete, and it is the first spec in this project verified end to end in a real signed-in browser.** The canvas now has an explicit tool mode: exactly one of `select`, `hand`, or the six shape tools is active at all times (no "no tool" state), the active tool owns the cursor, and the toolbar shows which one is active. This is the foundation specs **31** (Select) and **32** (Hand) build on; their *behaviors* are deliberately not implemented here — drag-on-empty-canvas still pans under every tool, exactly as before. **State (item 1)** new **`hooks/use-canvas-tool.ts`** owns the whole mode: the active tool, what a switch does to an in-flight gesture, and the V/H/R/Esc bindings. It is one hook rather than three, because those three things are the same concern — "which tool is active" is meaningless without "what happens to the gesture the last tool started". It must be called inside a `ReactFlowProvider`, since cancelling a connector reaches into the React Flow store. **Switching tools clears the in-progress gesture but *not* the selection** — a tool switch changes what the *next* click means, not what is currently selected. Today the only gesture that can be mid-flight is a connector dragged out of a handle (a shape placement is a single click; the marquee does not exist until `31`), cancelled via **`useStoreApi().getState().cancelConnection()`** — a store method, not a `useReactFlow()` one, which is why the hook reaches for `useStoreApi`. It is the single cancellation point, so `31`/`32`'s gestures land there rather than growing a second path. **Shape tools become modes (item 2)** clicking a shape in the toolbar now activates that *tool*; the next canvas click (`onPaneClick`) places the shape **centered on the click point** — the same hotspot the existing drop path uses, so click and drag feel identical — and the canvas returns to `select`. **Drag-and-drop is untouched and does not change `activeTool`** (verified: dragging a diamond while the hand tool was active left `hand` active). **The newly placed shape becomes the selection, and this works for a non-obvious reason worth recording.** The node is added as `{ ...node, selected: true }`, which is safe *only* because `selected` is declared **local-only** in Liveblocks' node config (`NODE_BASE_CONFIG` → `selected: false` in `@liveblocks/react-flow`'s `shared.js`): `LiveObject.from` routes local-config keys through **`setLocal`**, which keeps the value visible to `get()`/`toJSON()` **on this client only** and never writes it to Storage. So the placer's selection cannot clobber a collaborator's — the same invariant that makes `handleSelectionChange` broadcast selection through *presence* instead of the graph. It also survives React Flow's own pane-click deselect, because `resetSelectedElements()` runs **after** the `onPaneClick` callback and only emits changes for nodes **already in its store** — the new node isn't one yet. Confirmed in the RF source (`onPaneClick?.(event); store.getState().resetSelectedElements();`) and then in the live browser. **Toolbar (item 3)** `shape-panel.tsx` is **renamed to `tool-panel.tsx`** (`ShapePanel` → `ToolPanel`) — it no longer holds only shapes, and the code standards name files after the responsibility they contain. It now reads: select, hand, **divider**, rectangle, diamond, circle, pill, cylinder, hexagon — one row, reusing the existing pill container, `h-9 w-9` buttons, `h-5 w-5` icons, and the exact divider treatment already in `CanvasControls`. Active = **`bg-accent-dim text-brand`**, distinct from both rest (`text-copy-muted`) and hover (`bg-elevated`), using existing tokens only — no new color. The zoom/undo group is untouched and stays outside the tool system: **shape and cursor tools are peers because all eight own the cursor, and zoom/undo do not**. Buttons carry `aria-pressed` so the mode is exposed to assistive tech, not just to the eye. **Cursor (item 4) — the one place a Tailwind utility would have silently failed.** The cursor is driven by a **`data-canvas-tool`** attribute on the canvas wrapper plus four rules in `globals.css`, *not* a `cursor-*` class, for two reasons. First, the rule has to **out-specify React Flow's own `.react-flow__pane.draggable { cursor: grab }`** — a utility on the wrapper would lose to it and the cursor would never change. Second, scoping to the **pane** (rather than the wrapper) is exactly what leaves `.react-flow__handle.connectionindicator { cursor: crosshair }` intact, so **hovering a shape edge keeps the connector cursor whatever tool is active** — the spec's requirement is satisfied *structurally* rather than by a special case. **(Amended by `32`: still true for `select` and the six shape tools, but `hand` now gives connectors up, which drops the `connectionindicator` class and with it the handle's `pointer-events` — so under `hand` the handle is not a hit target and the pane's open hand shows through. Pane-scoping is what makes that fall out for free: the rule simply stops matching, and no CSS changed.)** **The specificity claim was checked against the compiled CSS, not reasoned about** — it is load-bearing, and Tailwind wrapping the selectors in `:where()` would have zeroed it and broken the cursor silently. The build emits `[data-canvas-tool=select] .react-flow__pane.draggable` at **(0,3,0)** against React Flow's **(0,2,0)**, **unwrapped**, and — the detail that makes specificity (not source order) the thing that matters — the two live in **separate CSS chunks**, so ours must win on specificity alone. `.dragging` follows `.draggable` in source so the hand **closes** while panning. **Keyboard (item 5)** `V`/`H`/`R` switch tools and `Esc` returns to `select` *and* cancels the in-flight gesture. **Cmd/Ctrl/Alt chords are excluded**, so `Cmd+V` still pastes rather than reaching for the select tool. Shortcuts are ignored while a text input has focus, via a new shared **`lib/editable-target.ts`** — the identical `isEditableTarget` helper already existed **twice** (`use-canvas-delete-keys.ts`, `useKeyboardShortcuts.ts`) and this would have been a third copy, so it was extracted and both existing callers repointed at it (a pure refactor; no behavior change). **Verified — and unlike `10`–`29`, this one got past the Clerk auth wall.** Every prior entry here records the editor as unexercised because the app is behind Clerk and the session had no credentials. Clerk is on a **development** instance (`pk_test`) and `CLERK_SECRET_KEY` is present, so a throwaway user was created through the **Clerk Backend API**, a **sign-in token** minted, and `/sign-in?__clerk_ticket=…` used to establish a real session — the documented way to authenticate a browser in tests. A real project was created and the **full Check-When-Done list was driven in the live app** (Liveblocks room connected, **0 console errors**): the canvas loads with `select` active; clicking each of the **eight** tools makes it the **only** active one with the right cursor (`default` / `grab` / `crosshair` read from `getComputedStyle`); a shape tool + canvas click **places the shape, returns the toolbar to `select`, and leaves the new node selected** (resizer visible); **drag-and-drop still places a node and leaves `activeTool` unchanged**; `V`/`H`/`R`/`Esc` all switch tools, while typing `r`,`h`,`v` into a node's label editor produced the text **"rhv"** and left the tool on `select`; the hand cursor **closes to `grabbing` while panning** and reopens after; and — the gesture test — a connector dragged out of a handle showed **2 connection-line elements**, pressing `H` **mid-drag** dropped that to **0**, and releasing the mouse created **no edge**. Plus `tsc --noEmit`, `npm run lint`, and `npm run build` all clean. **One finding worth recording, chased down rather than assumed:** `Esc` *does* clear the selection when a node holds **DOM focus** — but that is **React Flow's own pre-existing keyboard a11y** (`const unselect = event.key === 'Escape'` in its node keydown), **not** the tool system, which never touches selection. Proved by selecting a node **without** focusing it (via click-to-place): `Esc` then returns to `select` and the node **stays selected**, so the spec's "switching tools does not clear the current selection" holds for this implementation. **Cleanup:** the throwaway Clerk user and the QA project row were both deleted afterwards.
