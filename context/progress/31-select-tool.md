# 31 — select-tool

Spec: [`context/feature-specs/31-select-tool.md`](../feature-specs/31-select-tool.md)

- **`31-select-tool.md` — complete, and verified end to end in a real signed-in browser (0 console errors).** Selection, move, resize and delete are now the **select tool's** gestures rather than the canvas's, and empty-canvas drag — which used to pan — now draws a **marquee**. **Scoping the gestures (item 1) is four React Flow props, and one of them does more than it looks.** `elementsSelectable={isSelectTool}` and `nodesDraggable={isSelectTool}` turn click-select and move off under every other tool; `useCanvasDeleteKeys` takes a new `enabled` flag so Delete/Backspace go quiet too. **`elementsSelectable` is also what preserves the selection across a tool switch** — React Flow's `resetSelectedElements()` early-returns while nothing is selectable, so a pane click under the hand tool cannot clear what is selected. That is spec 30's "switching tools does not clear the selection" holding *structurally* rather than by a special case. Resizing needed a separate lever, because `NodeResizer` is rendered by the node and keys off `selected` alone: a new **`canvas-tool-context.ts`** publishes the active tool to the renderers inside the flow, and the resizer is withheld (`selected && isSelectTool`) rather than shown-but-dead. **A side effect of `elementsSelectable={false}` that was found in the browser, not reasoned about:** React Flow gives a node `pointer-events: none` when it is neither selectable nor draggable (its `hasPointerEvents` rule), so under another tool the node **body becomes click-through**. This is what makes "clicking a shape does not select it" true, and it is *load-bearing in both directions* — dragging a node body under `hand` now pans instead of moving it (right), and clicking a shape under a shape tool places a new shape on top of it (consistent with "clicking the canvas places that shape"). Confirmed the **handles are unaffected**: a descendant with `pointer-events: all` stays hit-testable under a `none` ancestor, so `.react-flow__handle` keeps `pointer-events: all` and its crosshair under *every* tool, and a connector still drags out and creates an edge while `hand` is active. Spec 30's connector-cursor guarantee and this spec's "connector creation is unaffected" both survive. **(Superseded by `32`, and the reason it held is not the reason assumed here.** `32` requires that `hand` give connectors up, so handles are now non-connectable — and therefore not hit targets at all — under `hand` alone; every other tool is unchanged. The deeper correction: this entry read "handles are unaffected" as a *property of the CSS cascade*, when it was really React Flow's `Handle` **defaulting its own `isConnectable` to `true`** and never reading the store — the node renderer had simply never forwarded the prop. So the handles were connectable under `hand` not because nothing had turned them off, but because **nothing could have**. See the `32` entry.) **The marquee is hand-rolled (`hooks/use-canvas-marquee.ts`), and React Flow's own `selectionOnDrag` was rejected for a concrete reason, not a stylistic one.** RF's marquee cannot be made additive or cancellable: it calls `resetSelectedElements()` the moment the drag crosses its threshold, and — the decisive part — `getSelectionChanges` writes `selected` **straight into the internal `nodeLookup`** (its own source comments call it "this hack"), which is **the object `NodeWrapper` renders from** (`useStore((s) => s.nodeLookup.get(id))`). The obvious fix — intercepting the `select` changes on their way to Liveblocks — **would not have worked, and this was checked rather than assumed**: `adoptUserNodes` only rebuilds an internal node when the user node's **object identity changes** (`checkEquality`), and Liveblocks' `useStorage` snapshots are **structurally shared**, so a node whose change we dropped keeps its identity and React Flow happily **reuses the mutated internal node** — the baseline would have silently flickered out of the selection mid-drag. So the marquee owns its rectangle and its hit-testing, and drives selection the one way already proven to work: **`select` changes through the Liveblocks-backed handlers**, exactly what a click on a node emits (`selected` is local-only in Liveblocks' node config, so a marquee cannot clobber a collaborator's selection). Hit-testing is a plain AABB **overlap** in flow coordinates (both corners run through `screenToFlowPosition`, so it is correct at any pan/zoom) — *intersects*, not contains, per the spec. `selectionKeyCode={null}` + `multiSelectionKeyCode="Shift"` is **not cosmetic**: RF binds its marquee to Shift by default, and leaving it bound would have made shift-click on a shape start a marquee (it `stopPropagation`s on a node target) instead of adding to the selection. Shift now means "add" for both a click and a marquee. The click a marquee leaves behind is swallowed in a capture handler — RF answers a pane click by clearing the selection, which would undo the marquee — and the guard is **spent by the next `pointerdown`**, because a marquee released *outside* the canvas produces no click at all and would otherwise leave the guard armed to eat an unrelated click later. Cancellation lands in **`selectTool`**, which spec 30 established as the single point where an in-flight gesture is cleared, so `Esc` *and* every tool switch abandon a marquee and put back the selection it started from. **Panning — a real gap in the spec, raised before implementing; the user chose.** The spec says "scroll and trackpad pan continue to work", but scroll did **not** pan: no `panOnScroll` prop was set, so React Flow's default had the **wheel zooming**. Since `select` gives up drag-to-pan, taking the spec literally would have left the default tool with no pan at all. The user chose to enable **`panOnScroll`** (the Figma/Miro model: wheel and two-finger trackpad pan, pinch and Cmd/Ctrl+wheel zoom), making the spec's own note — "pan moves to hand, hold-space, and scroll" — literally true. **One regression caught by the browser, not by the types.** Placing shapes in a row left them **all** selected: spec 30's "the newly placed shape becomes the selection" was quietly relying on React Flow's pane-click reset to clear the previous one, and that reset is a no-op while a shape tool is active (nothing is selectable then — the very property this spec adds). `handlePaneClick` now clears the previous selection **explicitly** instead of leaning on that side effect, which is the more honest code regardless. **Cursor:** under `select` the pane no longer carries React Flow's `.draggable` class (`panOnDrag` is off), so the spec-30 rule stopped matching and now targets the **bare pane**. Verified against the **compiled** CSS rather than reasoned about, since spec 30 flagged this as load-bearing: the rule emits **unwrapped** as `[data-canvas-tool=select] .react-flow__pane{cursor:default}` (0,2,0), and React Flow only ever sets a pane cursor on `.draggable` / `.selection` — **neither of which the pane carries under `select`** — so there is no specificity contest left to lose. **Verified in the live app** (throwaway Clerk user + sign-in ticket + project, all deleted afterwards), driving real mouse and key events: click selects / click-empty clears; **shift-click adds *and* removes**; a marquee that clips only a shape's **corner** selects it (proving *intersect*, not contain), highlights live during the drag, and clears on release; **shift-marquee adds, with the prior selection staying lit throughout the drag** (no flicker — the thing RF's own marquee could not do); a **2px** drag clears the selection and leaves no rectangle; **`Esc` mid-marquee restores the prior selection and its release does not re-clear it**; a connector drags out of a handle, creates an edge, and **never starts a marquee**; clicking a shape under `hand` or a shape tool does not select it; Delete does nothing under `hand` and deletes under `select`; and **wheel pans while zoom is unchanged**, with Ctrl+wheel still zooming (2 → 0.5). Plus `tsc --noEmit`, `npm run lint`, and `npm run build` all clean. **Not done (deliberately, per scope limits):** hold-space pan is spec 32; no copy/paste/duplicate/group/align; no lasso or right-click selection; selection outlines and resize handles are unchanged.

### Follow-up — 2026-07-14

- **Marquee QA follow-up — a real multi-pointer bug found by code review, reproduced on a real touchscreen, and fixed; the reported fix was necessary but not sufficient.** CodeRabbit flagged that `useCanvasMarquee` (`hooks/use-canvas-marquee.ts`) checks `event.isPrimary` only at the *press*, while the `pointermove`/`pointerup`/`pointercancel` listeners it binds on `window` accept events from **any** pointer — so a second contact's moves feed `handleMove` as though they were the first one's, and its release ends a drag still under way. The diagnosis is correct, and **it is reachable through an ordinary gesture rather than an exotic one**: under `select`, `panOnDrag` is off, so a one-finger drag on empty canvas is *ours*; `zoomOnPinch` is on by default; and the first finger of a **pinch-zoom** therefore always lands on the pane and arms a marquee before the second finger arrives. **Reproduced** (real multi-touch through CDP `Input.dispatchTouchEvent` + `Emulation.setTouchEmulationEnabled`, in the live signed-in app, against the pre-fix code): finger 1 pressed empty canvas and barely moved — no rectangle, nothing selected — then finger 2 landed and swept across the shapes, and **a marquee rectangle appeared and a shape was selected**, entirely from finger 2's coordinates, on a gesture finger 1 never made; the selection **survived both fingers lifting**. So a pinch-zoom silently changed the selection. **The prescribed fix — filter the listeners by `pointerId` — is necessary but does not finish the job**, and applying only it would have left a subtler version of the same bug: the foreign pointer stops corrupting the rectangle, but **finger 1 keeps drawing a marquee straight through the pinch**, so the zoom still ends in a spurious selection. A second pointer landing mid-gesture *means the gesture was never a marquee*, so it now **abandons** the marquee outright (via the existing `cancelMarquee`, which restores the selection it started from) rather than merely being ignored. Both halves live in the gesture: `Gesture` carries the `pointerId` that started it, `handleMove` and the `pointerup`/`pointercancel` handler answer to that id alone, and the existing `window` `pointerdown` capture listener — which already spent the click guard — now also cancels on a foreign pointer. That listener runs on `window` in the **capture** phase, *ahead of* the React handler that arms a gesture, so the press that starts a marquee finds `gesture.current` still `null` and **cannot cancel itself** — load-bearing ordering, and the reason the cancel could be folded into the listener that was already there instead of adding a second one. **No desktop behavior changes**: a mouse keeps one constant `pointerId`, so every guard added here is a no-op for it. **Verified:** the *identical* touch script that selected a shape before the fix now leaves the selection completely untouched (no rectangle, 0 selected, throughout and after), while a genuine **one-finger** marquee still draws and selects normally; plus all 12 of `31`'s desktop marquee behaviors re-driven with a real mouse (rect drawn, both shapes selected, click-to-clear, prior selection staying lit through an additive **shift-marquee**, and `Esc` mid-drag restoring the prior selection without its release re-clearing it). `tsc --noEmit`, `npm run lint`, and `npm run build` all clean.
