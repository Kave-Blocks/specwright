# 33 — architecture-interview

Spec: [`context/feature-specs/33-architecture-interview.md`](../feature-specs/33-architecture-interview.md)

### Direction

- **Direction behind the unit (`33`).** Set with the user: Specwright gains a **Discovery phase** in front of the existing flow, making the spine **Discovery → Design → Spec**. It is being built as an **internal accelerator for the 2-person team first**, and productized for other developers only if it proves useful. The user's original vision — a multi-agent research fleet (a manager dispatching groups of specialist agents, labeling/critiquing them in a loop, shown live) — is **deliberately deferred** as over-built for a 2-person internal tool: multi-agent systems use ≈15× the tokens of a chat and pay off only for high-value, heavily parallel work, and the live orchestration UI is product/demo value the team doesn't need to watch. The first increment — a lean **walking skeleton**, now built (see the entry above) — is a guided **architecture interview** (7 core questions + 1 optional) that composes a deterministic, structured project brief and feeds it to the existing `POST /api/ai/design` path in place of a one-line prompt — **no new route, background task, model call, or persistence**. AI pre-fill/enrichment of answers, persisting the brief, emitting specs in the project's own `feature-specs/` format, and any agent fan-out/critique loop are all explicitly **later units**. **Open question to validate before or alongside the build:** is planning actually the team's bottleneck, or is it implementation/testing/deployment? Full rationale and verified sources live in the strategy artifact *"Specwright — Discovery Phase: Build vs. Earn"* (Anthropic multi-agent + effective-agents, Fowler on YAGNI, Cockburn's walking skeleton).

### Outcome

- **`33-architecture-interview.md` — complete. The Discovery phase now has its walking skeleton: a guided interview that composes a structured brief and feeds it to the existing design path.** Three pieces. **(1) `lib/architecture-brief.ts`** — the question catalog, the answer model, and `composeBrief`, all pure: no React, no Liveblocks, no `@xyflow/react`, no model call, no clock, no randomness. **Every option set's key union is *derived* from its `as const` array** (`type ActorKey = (typeof ACTOR_OPTIONS)[number]["value"]`) rather than declared beside it, and the composer prints option **labels resolved through that same catalog** — so adding an option really is a one-line change that the type, the chips, and the brief all follow automatically, with no second place to update and nothing to drift. That is a different bounding idiom than `payload.ts`'s `Record<CanvasNodeShape, true>`, and deliberately so: `payload.ts` must stay in sync with a type it does **not** own (`CanvasNodeShape`), so it needs a compile-time *guard*; here the catalog **is** the source of truth, so derivation removes the possibility of drift instead of detecting it. **(2) `components/editor/ai/architecture-interview.tsx`** — the stepped Dialog (8 questions + Review = 9 steps), following `spec-preview-dialog.tsx` for the Dialog/`ScrollArea`/`rounded-3xl` scale **and for mounting the body only while open**, so closing unmounts the answers and a fresh interview needs no reset effect. **(3)** a "Guided brief" entry in `ai-architect-tab.tsx` next to the freeform input. **Assumptions are recorded per *field*, not per question — a deliberate reading of the spec, not an oversight.** The spec says "one line per question", but a question like Scale has two fields: answer the tier, never touch the growth pattern, and a question-level check would call the whole question answered and **silently apply the growth default** — which is precisely the failure mode the `## Assumptions` section exists to prevent. Per-field disclosure serves the stated purpose; per-question would defeat it on exactly the half-answered case. **Equality against `DEFAULT_ANSWERS` is the test**, so explicitly choosing the default and skipping the step compose an identical brief — which is also what the UI shows, since defaults render as **already-selected chips**, making "skipped" and "chose the default" indistinguishable by design rather than by accident. **One composition rule was added that the spec did not call for:** the interview's `idea` answer is pre-filled from the freeform prompt (so the user doesn't retype it), which would make `## Summary`'s verbatim restatement of `initialIdea` a duplicate of `## Users & Scope`'s first line. The restatement is therefore **skipped when the two are still identical** and kept the moment the user refines the answer — at which point both are genuinely worth having. **The Generate button's color follows the code the spec points at, not the class name it names.** The spec says `bg-accent text-white`, "the same accent button treatment as the existing send action" — but in this codebase `--accent` is `var(--bg-elevated)` (shadcn's neutral hover token), so `bg-accent` would render a **dark gray button**, and the existing send action is `bg-accent-green text-(--bg-base)`. `ui-context.md` also states outright that text on green must be `var(--bg-base)`, **never light text**, so `text-white` would violate a documented rule. Built as `bg-accent-green text-(--bg-base)` — the referent, not the label. **The only change to existing code is that `send()` now returns `Promise<boolean>`** (true once the run is under way). It is the single submit path for both entries, and the interview needs to know whether the hand-off actually happened: on success the dialog closes, on failure it stays open with its error. The freeform callers ignore the value, so their behavior is unchanged. **The dialog closes on a successful hand-off rather than holding the user through the run** — a deliberate reading of "loading tied to run status": the tab's status strip and disabled input are already the established place a run in flight is watched, and trapping the user behind a modal for a 30s generation would hide the canvas the run is drawing on. **Verified — but not the way `30`–`32` were, and the gap matters.** The tracker's usual QA path (throwaway Clerk user + sign-in ticket) was **blocked by this session's permission classifier**, and there was no existing signed-in session, so the editor behind the Clerk wall was unreachable. Instead: **17 unit checks on `composeBrief`** driven through `tsx` with no browser (determinism across calls and across equal-but-distinct objects; all ten sections present and in order; fully answered → no assumptions; skip-all → exactly one assumption per field, 18/18; a half-answered question still disclosing its untouched sibling; choosing the default ≡ skipping; 50k-char input truncating rather than rejecting and the brief staying bounded; the initial-idea dedupe in both directions; multi-select being order-independent and printing in catalog order) — **all pass**. Then the **component itself driven in a real browser** through a temporary public harness page, since deleted with `proxy.ts` reverted and **confirmed by an empty `git diff`**: the dialog opens pre-filled from the freeform input, Back is disabled on step 1, all 9 steps are reachable and every one skippable, multi-select **adds and removes** while single-select **replaces**, Review drops Skip/Next for Generate, a hand edit **survives Back/Next navigation** but is **recomposed away by an actual answer change** (which also moves that field out of `## Assumptions`), and Generate submits **the edited text verbatim** and closes the dialog — **0 console errors**. The tokens were read from `getComputedStyle`, not assumed: selected chip `rgba(0,200,212,0.12)` / `rgb(0,200,212)` (`bg-accent-dim` / `text-brand`), rest `rgb(30,30,35)` / `rgb(128,128,144)` (`bg-subtle` / `text-copy-muted`), Generate `rgb(98,192,115)` on `rgb(8,8,9)` (`--accent-green` on `--bg-base`) — **no new colors**. Plus `tsc --noEmit`, `npm run lint`, and `npm run build` all clean. **Not exercised — the honest gap:** no real design run was started through `POST /api/ai/design` from the interview, because that path is behind the auth wall. What backs it is that **the submit is not new code** — `onGenerate` is `send` itself, unchanged apart from its return value, so the interview cannot have a second generation path to get wrong. **One pre-existing behavior worth recording, measured rather than assumed:** the chat feed caps a message at `AI_CHAT_MAX_LENGTH` (2000) and `useAiChat.sendMessage` **truncates** to it, while the full text goes to the design run. A typical brief is **1265 chars** and a skip-everything brief **1729** (longer, because the assumptions list grows as the answers shrink), so both fit; a brief with **every** free-text field pushed to its 400-char cap reaches **4521**, at which point the *feed copy* is cut while the *run* still gets everything. That is how any long freeform prompt already behaves — not a regression — but the interview makes long prompts ordinary rather than rare, so it is the line to revisit if the chat record needs to match what was generated from.
