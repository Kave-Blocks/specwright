# 27 — spec-generation-flow

Spec: [`context/feature-specs/27-spec-generation-flow.md`](../feature-specs/27-spec-generation-flow.md)

- `27-spec-generation-flow.md` — complete. The spec-generation backend: trigger route, token route, durable task, and run ownership. Frontend, spec-editor UI, and persistence are all explicitly out of scope and were not touched (scope limits honored — nothing stores the spec yet). **Provider deviation (user decision, same as `23`):** the spec's Implementation says "uses Gemini through `@ai-sdk/google`", but `.env.local` still carries **only `OPENAI_API_KEY`** — there is no Google key, and no Gemini code exists anywhere in the project. Asked, and the user chose **OpenAI, matching `23`**, so `lib/spec-agent/generate.ts` reuses the exact `createOpenAI` + `gpt-4o-mini` pattern from `lib/design-agent/plan.ts` (`@ai-sdk/google` remains an unused dependency). The spec's "reuse existing … Gemini patterns" note is therefore satisfied by reusing the existing *provider* pattern; switching to Gemini later is a one-line model swap in `generate.ts`, since nothing else in the unit knows the provider (no new AI abstraction was introduced — also a scope limit). **Shared payload contract (the structural decision)** new **`lib/spec-agent/payload.ts`** owns the Zod schemas, and *both* the route and the task validate against them. It lives in `lib/` rather than in the task module because the route must not import the task instance (that would pull the AI SDK and the whole task graph into the request bundle — the type-only-import rule from `22`), yet both sides need the identical contract. `specRequestSchema` = `{ roomId, chatHistory, nodes, edges }`; `generateSpecPayloadSchema = specRequestSchema.extend({ projectId })` is what the task validates. **`projectId` is deliberately absent from the request schema** — the room id *is* the project id, so a client-supplied `projectId` would be an unverified claim; `z.object` **strips** unknown keys, so an attacker-supplied `projectId` in the body is physically discarded before the handler can read it, and the id that reaches both `tasks.trigger` and `prisma.taskRun.create` is the one **`getAccessibleProject(roomId, identity)` returned**. The node/edge/chat schemas are narrowed to just the fields the model reasons about (node → `id`/`position`/`data.label`/`data.shape`; edge → `id`/`source`/`target`/`data.label`; chat → `role`/`content`), so React Flow's render-only keys (`measured`, `selected`, `markerEnd`, styling) and the feed's `sender`/`timestamp` are stripped rather than shipped — the run payload stays small and the model isn't fed noise. A happy consequence: **the client can post its `ai-chat` feed messages and its canvas nodes/edges verbatim**, with no reshaping, which is why no frontend logic was needed. Array caps (`100` messages / `300` nodes / `600` edges) bound what one request can push into a run. `roomId`/`projectId` use `z.string().trim().min(1)` — the trim was **added after a test caught it**: `min(1)` alone accepts `"   "`, which would reach the access check as a lookup that can never match, whereas the other AI routes' `normalizeId` trims. **Trigger route (item 1)** `app/api/ai/spec/route.ts` (`POST`) — auth (`getClerkIdentity` → 401) → validate (`specRequestSchema.safeParse` → 400) → **resolve access from `roomId` alone** (`getAccessibleProject` → 404, owner **or** collaborator, mirroring the collaborative canvas the spec is written from) → `tasks.trigger<typeof generateSpec>("generate-spec", …)` via a **type-only import** → `prisma.taskRun.create({ runId: handle.id, projectId: project.id, userId })` → `{ runId }` (201). It returns **only `runId`**, per spec — unlike `/api/ai/design`, which also hands back `handle.publicAccessToken`; the spec provisions a dedicated token route for this flow, so the token is minted there. **Token route (item 2)** `app/api/ai/spec/token/route.ts` (`POST`) — the same `withAuth` + `TaskRun`-ownership shape as `/api/ai/design/token` (missing run → 404, wrong owner → 403, mirroring the 404/403 masking), minting a run-scoped read token `auth.createPublicToken({ scopes: { read: { runs: [runId] } }, expirationTime: "1hr" })`. The **1-hour expiry is the one difference** from the design token route (which takes the SDK's short default) and is what the spec asks for: a spec run is a longer read — the client may sit on the page while it is written and then re-read the finished Markdown. The two token routes are ~20 near-identical lines; they were **not** factored into a shared helper because their expiries differ and touching the design route is out of scope. **Task (item 3)** `trigger/generate-spec.ts` — a **`schemaTask`** (id `"generate-spec"`), the first in the project: `22` used a plain `task` explicitly because "zod is not installed", but `25` installed it, so the spec's "validate input with Zod" is satisfied by the SDK's own mechanism rather than a hand-rolled check (a validation failure throws `TaskPayloadParsedError` and **skips retrying** — a malformed payload is not transient). Retries/logging/error handling follow `design-agent.ts` exactly: no task-level `retry` (inherits `trigger.config.ts`'s `maxAttempts: 3`), `logger.info` on start/finish + `logger.error` on failure, a missing `OPENAI_API_KEY` throws **`AbortTaskRunError`** (a config error → no retry), and everything else rethrows so Trigger retries transient failures. **Realtime tracking uses Trigger *run metadata*, not a Liveblocks feed** — `metadata.set("phase", …).set("text", …)` through a small `setPhase()` helper, with the phase vocabulary **reused** from `types/tasks.ts`'s existing `AiStatusPhase` (`start`/`processing`/`complete`/`error`) instead of inventing a parallel enum. This is a deliberate split from `design-agent`, which broadcasts to the shared `ai-status-feed`: the design agent mutates the **shared canvas**, so every participant must see its progress, whereas a spec run produces a **document for the person who asked for it**, so its status rides on the run they alone hold a token for. The exported `SpecRunMetadata` interface is colocated with the producer for the consumer unit to import (a type import is erased at build, so the task never enters the client bundle). **Output is the Markdown string itself** (`run: async (payload): Promise<string>`), per "returns the generated spec content as task output" + "keep the task output as plain Markdown" — status lives on the metadata, so it does not need to be wrapped in a result object. `generateSpecMarkdown` prompts for a fixed section order (Overview → Architecture → Components → Data Flow → Technical Considerations → Open Questions), re-teaches the model the 6 shapes' semantics (reused from `plan.ts`'s prompt, so a cylinder still means a database when the spec is written), and instructs it to record what the canvas leaves undecided under Open Questions **rather than inventing decisions**. It also **strips a wrapping code fence** if the model emits one despite being told not to — a stray ` ```markdown ` wrapper would otherwise render the entire document as one code block downstream. **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean (both new routes registered as dynamic function routes `ƒ /api/ai/spec` + `ƒ /api/ai/spec/token`); a **17-group unit test** of the payload schemas (real sidebar body accepted; feed-only and render-only keys stripped; empty canvas/conversation allowed; missing/empty/whitespace-only `roomId` rejected and a padded one trimmed; missing or non-array `chatHistory`/`nodes`/`edges`, bad chat role, empty + 2000-char-boundary + over-long content, endpoint-less edge, and non-numeric node position all rejected; all three size caps enforced at their boundaries; **a client-supplied `projectId` never survives the request schema**; and the task schema requires the server-resolved `projectId` and round-trips the exact payload the route triggers with) — all pass; plus a **live dev-server smoke test** — unauthenticated `POST` to both routes returned clean `401 {"error":"Unauthorized"}`, proving they compile and run and that the auth guard fires before any DB or Trigger.dev work, with no compile errors in the dev log. **Not exercised authenticated end-to-end:** the real trigger → OpenAI → Markdown round-trip needs the Trigger.dev dev worker running with `OPENAI_API_KEY` in the **Trigger.dev environment** (task env comes from Trigger's env store, not Next's `.env.local`) and a signed-in session — the routes sit behind the Clerk auth wall and this session has no credentials, the same constraint as `10`–`26`. The trigger/persist/token/generate paths are verified structurally (types/build/lint + the schema unit test + the unauth smoke test) and traced against the pinned `@trigger.dev/sdk@4.5.3` (`schemaTask`, `metadata.set` inside `run()`, `auth.createPublicToken`'s `expirationTime`), not via a signed-in run.

### Follow-up — 2026-07-13

- **Spec payload QA follow-up — unbounded node/edge strings bounded, but with a per-field split the reviewer's patch got wrong.** CodeRabbit flagged that `specNodeSchema`/`specEdgeSchema` (`lib/spec-agent/payload.ts`) bound only the *count* of objects (`MAX_NODES = 300`, `MAX_EDGES = 600`) and not the *size* of the strings inside them: `id`, `label`, `shape`, `source`, and `target` were all unbounded, so up to **900 objects each carrying arbitrarily large strings** could be posted, forwarded verbatim into the `generate-spec` prompt (`buildUserPrompt`), and charged as tokens. The finding is **real and worth fixing** — the array caps gave a false impression of boundedness. It reproduced: a 900-object payload of 100k-char labels (**~90 MB of label text**) parsed cleanly and would have gone straight to the model. **But its prescription — "apply the same bounding pattern used for `content` here" (`.max(500)` on every string) — is wrong for `label`, and would have introduced a regression.** `content` can safely *reject* over-length input **only because its producer already guarantees the bound**: `use-ai-chat.ts` does `slice(0, AI_CHAT_MAX_LENGTH)` before writing to the feed, so a real client cannot exceed it. Node labels have **no such guarantee** — they are typed into a plain `<textarea>` with **no `maxlength`** (`canvas-node.tsx`) and stored in Liveblocks — so `.max(500)` + reject would let **one long label on one node hard-400 the entire spec run for an otherwise legitimate canvas**. So each field is bounded by *what produces it*: **ids** (`crypto.randomUUID`, machine-generated — nothing legitimate approaches the cap) are **rejected** over `MAX_ID_LENGTH = 200`; **labels** (human-typed, uncapped at the source) are **truncated** to `MAX_LABEL_LENGTH = 500`, never rejected. **`shape` is bounded by domain, not by length — strictly stronger than the proposed `.max(50)`.** The value is fed to the model as the node's *meaning* (a cylinder **is** a database — the system prompt teaches all six), so an arbitrary 50-char string is not merely large, it is **nonsense the model would try to interpret**, and a plausible prompt-injection surface. It is now `z.enum` over the six real shapes, with `.catch("rectangle")` — the same coercion `resolveShape` already applies in the design agent — so **stale or hostile storage degrades instead of failing a valid run**. The enum is keyed off a **`Record<CanvasNodeShape, true>`**, so adding a seventh shape to the canvas **fails to compile here** rather than silently degrading every spec to `rectangle`; the same `Record<CanvasNodeShape, …>` idiom is already used in `shape-panel.tsx`. `CanvasNodeShape` is a **type-only import** and therefore erased at build — load-bearing, because `@/types/canvas` pulls in **`@xyflow/react`** at runtime, and this module is imported by the route *and* the client, which is exactly the bundle coupling its docstring exists to prevent. **Verified:** `tsc --noEmit` and `eslint` clean; a **9-check unit test** (a real canvas node passes untouched with render-only keys stripped; an over-long label truncates rather than rejects; an over-long id rejects; a hostile 15k-char `shape` coerces to `rectangle`; all six real shapes pass through unchanged; edge endpoints and edge labels bounded the same way; over-long chat `content` **still rejects**, unchanged) — all pass, and the headline case now bounds **90 MB of submitted labels down to a 502 KB payload**. The compile-time drift guard was **proven, not assumed**: temporarily adding a `"triangle"` shape to `CanvasNodeShape` produced exactly `payload.ts(58,7): error TS2741: Property 'triangle' is missing`, and `types/canvas.ts` was restored (no diff). The route was checked to destructure from **`parsed.data`** (not the raw body), so the truncated/coerced values are what actually reach `tasks.trigger` and the prompt — the fix is effective end to end, and the task re-validates with the same schema. **Deliberately NOT fixed — and the reviewer's framing is misleading here:** field caps **cannot bound the request body at all**. `readJsonBody` does `await request.json()`, which reads and parses the **entire body into memory before Zod ever runs** — so the "very large request body" half of the finding is untouched by this change (what *is* fixed is everything downstream: the Trigger payload, the prompt, and the token bill). Bounding the body needs a `Content-Length`/stream guard in the route, which is mitigated in practice by the platform (Vercel caps serverless request bodies at ~4.5 MB) and by the route being **authenticated and membership-checked** — this is an authenticated member burning their own project's tokens, not an anonymous DoS. Worth a follow-up if the app is ever self-hosted without a proxy body limit.
