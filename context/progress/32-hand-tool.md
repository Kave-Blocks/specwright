# 32 — hand-tool

Spec: [`context/feature-specs/32-hand-tool.md`](../feature-specs/32-hand-tool.md)

- **`32-hand-tool.md` — complete, and verified end to end in a real signed-in browser (0 console errors). Panning is now its own tool, and hold-space reaches it from anywhere.** Most of item 1 was already true from `30`/`31` and got a *confirmation* rather than an implementation: under `hand` the nodes are `pointer-events: none` (React Flow's `hasPointerEvents` rule, since nothing is selectable or draggable), so a drag on top of a shape already panned; `elementsSelectable={false}` already kept the selection alive-but-inert; and `useCanvasDeleteKeys(_, isSelectTool)` already silenced Delete. **The one behavior genuinely missing was the connector — and getting it took two fixes, the first of which silently did nothing.** `nodesConnectable={!isHandTool}` on `<ReactFlow>` looked like the whole job and *was not*: in the live browser the handle still carried `connectionindicator` and its crosshair, with `nodesConnectable: false` sitting right there in the store. **React Flow's `Handle` never reads the store.** `NodeWrapper` resolves connectability per node (`node.connectable || (nodesConnectable && node.connectable === undefined)`) and hands it to the *custom node component* as an `isConnectable` prop — but `HandleComponent` signs itself `isConnectable = true` **as a parameter default**, so a handle left to itself stays connectable no matter what the flow says. `CanvasNodeRenderer` had never forwarded it (the prop was simply unused, which is why **TypeScript could never have caught this** — and why it took the browser to find). The pre-fix behavior was worse than "connectors still work", because two React Flow subsystems disagreed: `ConnectionLineWrapper` **does** read the store (`renderConnection = !!(width && nodesConnectable && inProgress)`), so the connector started **invisibly**, and the handle carries **`nopan`** — which RF's own pan filter honors — so **the pan was blocked too**. A drag off a shape's edge under `hand` did nothing at all: not the connector, not the pan, i.e. the one gesture the hand tool exists for, dead on exactly the pixels the spec calls out. Forwarding `isConnectable` to all four `<Handle>`s fixes it *structurally*: no `connectionindicator` → the handle falls back to React Flow's base `.react-flow__handle { pointer-events: none }` → it stops being a hit target → **the pane becomes the drag target**, so the drag pans, the cursor is the pane's open hand, and no connector starts. Confirmed by hit-testing: the element under a shape's edge is now literally `react-flow__pane`. **This is also why item 3 (cursor) needed no new CSS at all** — the same mechanism that kills the connector hands the cursor to the pane, so `30`'s crosshair rule stays untouched and simply stops matching. Verified *unregressed* under the other tools: `select` and the shape tools keep connectable handles, the crosshair, a live connection line, and a real edge on drop. **Edges were the second thing still answering the pointer under `hand`, and the spec's own wording forced the issue** ("it is simply not editable"; "open hand while `hand` is active"). React Flow marks a non-selectable edge `inactive`, but that only sets `pointer-events: none` on the `<g>` — and `CanvasEdgeRenderer` re-enables pointer events **inline on descendants** (the hit path is `pointerEvents: "stroke"` + `cursor: "pointer"`, the label is `pointerEvents: "all"`), which beats an ancestor's `none`. So under `hand` an edge kept a **pointer cursor**, stayed **double-click editable**, and — because the label carries **`nopan`** — **pressing on a label would have blocked the pan outright**. Both are now gated on the tool through the existing `useActiveCanvasTool()` context (the same lever `31` built for the resizer). The hover flag is handled by **deriving** `active` as `hovered && !isHandTool` rather than resetting state in an effect: a hit path that stops taking pointer events is hit-tested out from under the pointer and never gets its `mouseleave`, and the repo's `react-hooks/set-state-in-effect` rule rejects the effect anyway — the derivation is both lint-clean and the more honest statement (the tool is the authority on its own hover). **Hold-space (item 2) is a real change of `activeTool`, not a panning special case** — which is the whole design. Because the tool *is* `hand` while the key is down, the toolbar's `aria-pressed`, the `data-canvas-tool` cursor, `elementsSelectable`, `nodesDraggable`, `panOnDrag`, `nodesConnectable`, the marquee's arming, and the delete keys **all follow for free**; nothing needed a second code path. It lives in `useCanvasTool`, which already owned the keyboard. **React Flow was already binding space to pan, invisibly, and that had to be taken away from it.** `panActivationKeyCode` **defaults to `'Space'`** and is OR-ed straight into panning (`const panOnDrag = panActivationKeyPressed || _panOnDrag`). Left on it would be a *second, silent owner of space that disagrees with the first*: the spec says space mid-marquee is ignored, and our hook does ignore it — but RF's `useKeyPress` would still have flipped `panOnDrag` on, so the **next** press on empty canvas with space still held would have panned **and** marqueed at once. `panActivationKeyCode={null}` (with `null`, `useKeyPress` binds no listeners at all — checked in the source, not assumed) makes `useCanvasTool` the one owner of space. **The mid-gesture rule is one `dragging` ref, and it is load-bearing rather than merely polite.** Every gesture space must stay out of the way of — marquee, node move, connector, pan — is a primary-button drag, so a single flag fed by window `pointerdown`/`pointerup`/`pointercancel` covers all four without reaching into React Flow for three different in-progress states. It has to exist because **`hand` turns `nodesConnectable` off, and RF only renders the connection line while nodes are connectable** — so taking the hold mid-connector would have *deleted the connector out from under the drag holding it*. Proven in the browser: with space pressed mid-drag the connection line **survives** and the edge still lands. Three failure modes were closed deliberately: a **`dragend`** listener, because a native drag off the tool panel **swallows the `pointerup` entirely** and would otherwise strand the flag on and leave space dead for the rest of the session; a **`blur`** listener, because Cmd+Tab with space down never delivers the `keyup` and would strand the canvas on the hand tool; and an **explicit tool choice while space is held clears the hold**, so releasing the key cannot undo it. The release is **symmetric** with the ignore rule (the spec is silent, and this is the consistent reading): space let go mid-pan **defers** the return until `pointerup`, so the tool is never yanked out from under a drag in flight. `event.code === "Space"` is `preventDefault`ed unconditionally outside a text field — it stops the page scrolling *and* stops the still-focused toolbar button from re-firing its click. **Verified in the live app** (throwaway Clerk user + sign-in ticket + project, all deleted afterwards), driving real mouse and key events over a canvas of two shapes and a labeled edge: under `hand`, dragging empty canvas **and dragging on top of a shape** both pan while the shape stays put; the pane reads `grab` idle, `grabbing` mid-pan (`draggable dragging`), and **`grab` even over a shape and over an edge**; clicking a shape does not change the selection and Delete/Backspace remove nothing; a shape selected *before* the switch is **still selected**; no handle is connectable, a drag off a shape's edge **pans and creates no edge**, and double-clicking an edge **does not open its label editor** while the label still renders. Hold-space: from `select` it pans and returns to `select`; from a **shape tool** it pans, **does not place a shape**, and returns to that same shape tool; the toolbar flips to `hand` and back (`aria-pressed`), and the cursor with it. Mid-gesture: space during a **marquee** leaves the tool on `select`, the rectangle drawing, no pan, and the selection **identical to the same marquee run without space**; space during a **node move** lets the move complete; space during a **connector** leaves the line drawn and the edge is created. Space typed into a node's label **inserts a space and leaves the tool alone** (the label committed and survived a reload). Plus `tsc --noEmit`, `npm run lint`, and `npm run build` all clean. **Not done (deliberately, per scope limits):** scroll/trackpad panning, zoom, and fit are untouched; no zoom-to-selection or space-drag-to-zoom; no momentum, inertia, or animated panning; the viewport is still not persisted.
