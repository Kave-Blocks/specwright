# 38 — Build Units

A project keeps an ordered, human-owned list of build units — pieces of work a team intends to implement, each tracked to a status and verification level as work happens. This unit lays the persistent schema, wire types, and the start of the UI surface.

## What Has Shipped

### Schema and Migration

`prisma/models/project-build-unit.prisma` (new): `ProjectBuildUnit` with all fields per spec — id, projectId, sequence, key, title, summary, status, verified, source, createdAt, updatedAt. Three enums match the tracker vocabulary exactly: `BuildUnitStatus` (SPECCED/IN_PROGRESS/SHIPPED/DEFERRED/BLOCKED, default SPECCED), `BuildUnitVerified` (NONE/STRUCTURAL/PARTIAL/BROWSER, default NONE), `BuildUnitSource` (MANUAL/SPEC, default MANUAL). Both unique constraints in place: `@@unique([projectId, key])` and `@@unique([projectId, sequence])`. The latter is documented as serving also as the ordering index, requiring no separate `@@index`. Cascade relation to `Project` matches `ProjectSpec` and `ProjectCollaborator`.

`prisma/models/project.prisma` (edit): `nextBuildUnitSequence Int @default(1)` added, plus the `buildUnits ProjectBuildUnit[]` back-relation.

Migration `20260731033202_add_build_units` was generated by `npx prisma migrate dev` on the first attempt, with the shadow-database step succeeding against the hosted Prisma Postgres — neither fallback described in `context/progress/05-prisma.md` was needed. This is worth recording: that file documents a fallback using `--from-empty`, which only works for an **initial** migration; an incremental one needs `--from-config-datasource`, and Prisma 7 has removed `--from-url` entirely. The clean path worked here.

**Verified**: `npx prisma migrate status` confirms schema is up to date. A scripted `prisma db execute` assertion confirmed the `_prisma_migrations` row has `finished_at IS NOT NULL AND rolled_back_at IS NULL`; the table exists with the column `NOT NULL DEFAULT 1`; both unique indexes are present; and the foreign key is `onDelete: Cascade`. ### Wire Contract

### Build Units Hook

`hooks/use-project-build-units.ts` (new, `"use client"`): `useProjectBuildUnits(projectId)` exposing `units` / `isLoading` / `error` / `refresh` plus `create`, `update`, `remove`. Load path mirrors `hooks/use-project-specs.ts`: request inside the effect, reload key, request counter that drops a superseded response, `AbortController`. Each mutation applies the row the server returned to local state rather than refetching, so a status change does not blank the list and flash.

Two decisions worth recording:
- A mutation failure never sets `error` and never blanks `units` — it returns `{ ok: false, error }` only. This is what lets a refused rename surface a message with the list intact. Error text is read from the server's `{ error }` body through a helper whose `response.json()` is wrapped in try/catch, because the guard's 401/404 and an unhandled 500 are not guaranteed to carry JSON.
- `update` sends `JSON.stringify(patch)` directly rather than assembling the body key by key, because `JSON.stringify` drops `undefined` and that is exactly the presence semantics the route's `"field" in body` check expects — absent means leave alone, `summary: null` means clear. A later edit that "fixes" this into an explicit builder would reintroduce `summary: undefined` as a cleared field.

### Server Library

`lib/build-units.ts` (new): Five exhaustive `Record` maps bridge Prisma enums and the tracker's lowercase string vocabulary: status `Record<BuildUnitStatus, string>` (SPECCED/IN_PROGRESS/SHIPPED/DEFERRED/BLOCKED → 'specced'/'in progress'/etc.), verified `Record<BuildUnitVerified, string>` (NONE/STRUCTURAL/PARTIAL/BROWSER → 'none'/'structural'/etc.), and their inverses `Record<string, BuildUnitStatus | null>` etc. The source enum has only an outbound map (MANUAL/SPEC → 'manual'/'spec'); inbound parsing would be dead code since the client never sends source.

Parsing guards with `Object.hasOwn` before indexing to reject inherited keys — `'toString'` returns `null` rather than an `Object.prototype` function typed as an enum member. This was verified at runtime: the tests confirm the guard works as typed.

Constants: `MAX_BUILD_UNITS = 200` (runaway guard, not a product limit), `MAX_UNIT_TITLE_LENGTH = 200`, `MAX_UNIT_SUMMARY_LENGTH = 1_000`.

`deriveBuildUnitKey` reuses `slugify` from `lib/projects.ts` with fallback to `unit-{sequence}` — no duplicate slugifier per the earlier conflict resolution.

`createBuildUnit(projectId, { title, summary, status, verified })` enforces the pinned transaction order: increment counter (`UPDATE … RETURNING` acquires the `Project` row lock) → cap check → key derivation → insert. Cap rejection throws a private sentinel to force rollback; P2002 (unique constraint) is caught outside and returned as `{ ok: false, reason: "duplicate" }`. Does **not** re-truncate or reject on long inputs — expects title and summary already through `normalizeUnitTitle` and `normalizeUnitSummary`, because the empty-title 400 must be answerable at the route boundary.

`updateBuildUnit(projectId, unitId, patch)` does `findFirst({ where: { id, projectId } })` before the write, re-deriving the key from the fetched `sequence` on a title change. Returns `{ ok: true, unit }` or `{ ok: false, reason: "duplicate" | "not-found" }`.

`deleteBuildUnit(projectId, unitId)` is a scoped `deleteMany` returning a boolean.

`listBuildUnits(projectId)` lists units in sequence order with no `key` on the wire, following the `ProjectSpec.filePath` discipline.

**Verified at the database layer:** 32 checks passed on the first run against the live hosted Postgres, all using throwaway projects deleted afterwards. No module fixes were needed.

Covered: parallel creates receive different sequences (1 vs 2); delete-highest then create gives a higher number (deleted 2, new 3) rather than reusing. A punctuation-only title (`"!!! ??? ***"` → `key=unit-4`) and a non-Latin title (`"日本語のタイトル"` → `key=unit-5`) both create rather than failing. A 400-char title stores 200 chars; a 5000-char summary stores 1000. A duplicate title returns `{ok:false, reason:"duplicate"}` without throwing and does not burn a sequence number (previous 6, next 7). Rename into a taken title returns `duplicate`. Parsing `'in progress'` → `IN_PROGRESS` while `'in-progress'` and `'toString'` both → `null`. Updating or deleting a unit from a *different* project returns `not-found`/`false` without touching the foreign row. List order is by sequence with no `key` on the wire. Deleting a project removes its units (6 before, 0 after). Cleanup confirmed 0 leftover units and 0 leftover QA projects.

A two-way race is a weak sample, so the concurrency guarantee was stress-tested with **eight concurrent creates**. Assigned sequences came back interleaved (1, 4, 2, 6, 5, 3, 7, 8) but all eight distinct and contiguous 1–8, with the counter at 9 and 8 rows persisted. The interleaving with no collision proves the `Project` row lock serializes the creates — the evidence supporting the spec's "two units created in parallel receive different numbers" check.

**Note:** This evidence covers the **lib layer only**. The HTTP layer (membership guard, status codes, boundary normalization) remains unverified.

### HTTP Routes — Collection Endpoint

`app/api/projects/[projectId]/build-units/route.ts` (new): GET and POST collection endpoint.

**GET** — guards with `withProjectMember`, queries `project.id` from the guard-resolved context, calls `listBuildUnits(project.id)`, and responds `200 { units }`.

**POST** — same guard. Reads `title` and `summary` from body, normalizes both at the boundary through `normalizeUnitTitle` (whitespace-only, missing, or non-string → `null`; rejects on empty with `400 { error }`) and `normalizeUnitSummary` (whitespace-only/missing → `null`; no length check — over-length is stored truncated), then calls `createBuildUnit(project.id, { title, summary, status, verified })` with defaults. Maps the result: `400 { error }` on empty title, `409 { error }` on duplicate title, `409 { error }` on cap exceeded (message interpolates `MAX_BUILD_UNITS` from the constant, so the string cannot drift), `201 { unit }` on success.

**Key design decision recorded.** Spec item 5 names "catch Prisma's P2002 in the route" — but `lib/build-units.ts` already catches it and returns `{ ok: false, reason: "duplicate" }`, so both routes (this one and the single-unit PATCH) handle it identically. The route branches on that result instead of catching its own P2002. Same user-facing outcome; the placement follows the interface contract where the two documents diverge. A later reader comparing against spec item 5 will notice the missing try/catch and should find this explanation.

**Verified: HTTP layer, partial**

`npx tsc --noEmit` and `npm run lint` both exit 0.

Exercised against a live `npm run dev`, **unauthenticated**:
- `GET` → 401
- `POST` → 401
- `POST` with a blank title → 401 (guard runs before body parsing)
- `PUT` → 405 (method not implemented)

That proves three things: the file resolves at `/api/projects/{id}/build-units`, only `GET` and `POST` are exported, and — the useful one — the membership guard runs before any body parsing, since the blank-title request never reaches the 400 branch.

Boundary literals tested directly: whitespace-only, missing, or non-string title all normalize to `null`; punctuation-only title survives as-is; a 300-char title stores 200 chars; a 2000-char summary stores 1000.

**Explicitly NOT verified: Authentication paths**

All authenticated routes remain unproven. Clerk auth here is session-cookie based (`proxy.ts` runs `clerkMiddleware`, `withProjectMember` calls `getClerkIdentity`), and minting a session token would mean issuing real auth artifacts against the Clerk dev instance. So these paths are unverified:

- `404` for an authenticated non-member
- Collaborator (not owner) can POST

All of this requires a signed-in browser session to exercise.

### HTTP Routes — Single-Unit Endpoint

`app/api/projects/[projectId]/build-units/[unitId]/route.ts` (new): PATCH and DELETE single-unit endpoint.

**PATCH** — guards with `withProjectMember<{ projectId: string; unitId: string }>`, passing the guard-resolved `project.id` into the lib rather than the raw path param. Row scoping — ensuring a foreign unit id is unreachable — lives in `lib/build-units.ts`. Reads `status`, `verified`, `title`, `summary` from body.

Three implementation details worth recording because they are subtle:

- **Presence is `"field" in body`**, not an `undefined` check on the value. A body of `{ "summary": null }` normalizes to `null` (clearing the summary); a body of `{ "summary": "" }` also normalizes to `null`. But an absent `summary` key never reaches the patch object, so the column is left alone. A truthiness check here would silently make clearing impossible — `summary: null` would be treated as "not provided" and the column preserved. Only the presence check makes `null` and `""` both mean "clear" while absent means "leave it".
- **Every present field is parsed for validity before the nothing-to-update check.** A body carrying only `{ "status": "nope" }` answers `{ error: "Unknown status" }` rather than `{ error: "Nothing to update" }`. Validation happens first, idempotence check last.
- The empty-patch check is `Object.keys(patch).length === 0`, which is correct because a valid-but-null `summary` still writes a key into the patch object.

Normalization runs at this boundary — field values are parsed to enums, title and summary are passed through `normalizeUnitTitle`/`normalizeUnitSummary` — because the lib deliberately trusts what it receives. Calls `updateBuildUnit(project.id, unitId, patch)`. Maps the result: `400 { error }` on unknown status or verified values, `400 { error }` on empty title after normalization, `404 { error }` if unit not found or not in this project, `409 { error }` on key collision (duplicate title), `200 { unit }` on success.

**DELETE** — same guard. Calls `deleteBuildUnit(project.id, unitId)`. Answers `404 { error }` if unit not found or not in this project, `200 { ok: true }` on success. (Note: this is the `brief/route.ts` shape, deliberately not `{ success: true }` as in `projects/[projectId]/route.ts`. The repo is inconsistent here; this choice was pinned rather than left to chance.)

**Verified: HTTP layer, structural**

`npx tsc --noEmit` and `npm run lint` both exit 0 on the final tree (the collection route had landed previously; the second run covers both routes together).

Real HTTP against the running dev server, **unauthenticated**:
- `PATCH /api/projects/{id}/build-units/{id}` → 401
- `DELETE /api/projects/{id}/build-units/{id}` → 401
- `POST /api/projects/{id}/build-units/{id}` → 405

That proves the file is wired at `/api/projects/{projectId}/build-units/{unitId}`, exports exactly `PATCH` and `DELETE`, and that a signed-out caller gets 401 with no confirmation the project or unit exists.

**Explicitly NOT verified: Authenticated paths and presence semantics**

The authenticated paths need a browser session. The implementing agent attempted to reach them without one — this is a Clerk *test* instance (`sk_test`), so it tried to mint a session token through the Clerk Backend API and drive the route with a `Bearer` header. **The permission classifier blocked that call, and the agent did not route around it.** Record that here because it explains why the gap exists rather than leaving it looking like an oversight.

Unproven as a result:
- `200 { unit }` on a valid patch to `status` or `verified`
- Each of the four `400 { error }` messages (unknown status, unknown verified, empty title, nothing to update)
- The presence semantics end to end (that `{ "summary": "" }` clears and an absent `summary` preserves)
- `409 { error }` on a rename into a taken title
- `404 { error }` for an unknown unit id and for a unit id from another project
- `DELETE` → `200 { ok: true }` on success
- `DELETE` → `404 { error }` on a second delete of the same unit

The lib half of those behaviours (scoping, duplicate-on-rename, P2002 and P2025 mapping) is already proven against the real database in the `lib/build-units.ts` verification above. What remains unproven is specifically the mapping of those lib results onto HTTP status codes and body shapes, plus the boundary parsing and presence checking.

### Build Surface — View, Row, and Page

`components/editor/build/build-unit-row.tsx` (new): `BuildUnitRow({ unit, pendingAction, pendingChip, rowError, onUpdateStatus, onUpdateVerified, onRename, onDelete })` — a prop-driven, leaf component with no hooks. Renders the row number (padded to 2 digits), title with hover-to-edit, summary, status and verified badges (with pending spinners), expandable chips (5-way radio groups for each, with pessimistic selection), and Delete button. File-local `ValueBadge` (generic, rounded-full per C1 precedent) and `ChipRadioGroup<V>` (rounded-xl per spec, with pending spinner gating). Includes `displayEntry` helper mapping the wire vocabulary to display labels and CSS classes.

`components/editor/build/build-view.tsx` (new): `BuildView({ projectId })` — the Build surface root. Insets by `pl-(--canvas-inset-left,0px)` with a CSS transition; integrates the hook and manages expanded-row state. Single accordion at a time via `expandedUnitId` with a true toggle and a focus-loss guard (closes expanded row when focus leaves the row). `AddUnitForm` rendered inline at the top. List branching: `isLoading && units.length === 0` shows a loading state, `units.length === 0` shows empty, otherwise renders the list. Each row gets a `pendingAction` gate serializing mutations — no concurrent updates to the same row — plus row-scoped error state cleared at each attempt start.

`app/editor/[roomId]/build/page.tsx` (new): Server Component with the exact same shape as the Specs page. Awaits `params`, resolves `projectId` from the `roomId` through `getEditor`, renders `BuildView` with that `projectId`.

**Verified**: `npx tsc --noEmit` exit 0, `npm run lint` exit 0, and **`npm run build` exit 0** — the feature spec's own final check-when-done line. The build's route table lists `ƒ /editor/[roomId]/build` alongside both API routes. The implementing agent confirmed that refs spread through `components/ui` wrappers into Base UI actually attaches (critical for the focus management); verified by reading React's `coerceRef` in `node_modules`.

**Three implementation properties are load-bearing — do not "simplify" later:**

1. **A row-wide `pendingAction` gate serializes every mutation in a row.** This is correctness, not UX. `useProjectBuildUnits`'s `update()` returns the row by `id` with **no ordering guard** — unlike the list-load path, which has an explicit request counter. Without the gate, a status PATCH and a verified PATCH could resolve out of order and silently revert the field the later request changed. No concurrent mutations to the same row are allowed; the gate blocks the UI until the prior one settles.

2. **Chip selection is pessimistic, never optimistic.** The selected chip is always literally the value from props, so a failed mutation needs no rollback — the UI never showed the new value.

3. **`rowError` is cleared at the start of every attempt, before the `await`.** A stale error message from a previous failure never lingers beside an unrelated new action.

Also: badges are `rounded-full` (Planned-card shape, per C1) while chips are `rounded-xl` (C2). Deliberate.

## Deviations From The Spec

Four design conflicts between spec and codebase precedent were surfaced and resolved:

1. **Muted badge treatment.** Spec names "the Planned card and the share dialog's owner row" as one treatment for collapsed-row badges. Code inspection: the owner row uses `border-brand/30 bg-accent-dim text-brand` (brand-accented), while the Planned card uses `bg-subtle text-copy-muted`. Resolved to the Planned card's treatment (`bg-subtle text-copy-muted`), because this is what specs 39 and 41 both independently name as "the treatment 38 established" — consulting their specs revealed the intent. Specification item 11 will update the spec text to name only the Planned card.

2. **Chip radius.** Spec specifies `rounded-xl` for status and verification chips, but precedent (Discovery option chips and canvas tool panel) both use `rounded-full`. The spec wins on radius; UI details are explicit contracts and deviations cost clarity. `rounded-xl` is implemented.

3. **Architecture context section.** Spec says to place build-units routes "under the membership-gated group" in `context/architecture-context.md`, but that heading does not exist today. Created a new `## Build Units` section instead rather than inventing an intermediate heading. This is not recorded in the spec; spec 12 will note it if the heading arrangement changes.

4. **Key derivation.** Spec re-specifies the key derivation algorithm (lowercase, non-alphanumerics collapsed to single hyphens, trimmed, fallback to `unit-{sequence}`). `lib/projects.ts` already exports `slugify` implementing this character-for-character. Reuse it rather than write a second identical implementation.

Two open numbers in the spec were resolved without spec deviation:
- `MAX_UNIT_TITLE_LENGTH = 200` and `MAX_UNIT_SUMMARY_LENGTH = 1000`. Spec names the truncate-don't-reject policy but leaves bounds open; these match the Brief implementation's pattern.
- Verified-chip display order runs least→most rigorous (none → browser), the reverse of how `context/progress-tracker.md`'s tracker legend lists it. Display order takes precedence over legend order in UI lists.

## Build Surface Deviations from Design Spec

Six implementation details deviate from or extend the design spec, all recorded here because they are load-bearing:

1. **`autoFocus` on the rename input replaced by a transition-keyed effect.** Spec named `autoFocus`, but it fires on every *mount*, so re-expanding a row left mid-rename would pull focus off the header the user just activated — contradicting the design spec's own rule that focus stays on the header after toggling. Instead, an effect focuses the input on first entry only and restores focus to the Rename button on save or cancel.

2. **`inline-flex items-center gap-1.5` added to `CHIP_BASE`.** The pinned string carried no layout, so the pending spinner would sit on the text baseline. No visual change when no spinner is present.

3. **A fifth row state, `pendingChip: string | null`.** `pendingAction` distinguishes the group (`"status"` / `"verified"`), not which of five chips was clicked — and since selection is pessimistic, it is never the selected one. Gated so the two groups never spin simultaneously.

4. **An `id` added to the header button.** The focus-loss guard lives in `build-view.tsx` but the fixed `BuildUnitRowProps` gives the view no ref into the row; the guard resolves the header by id instead, reusing the id scheme already established for the panel.

5. **`aria-label` added to the rename `Input`.** The design spec's markup left it unnamed.

6. **The rename form replaces the whole action row, so Delete is hidden while renaming.** The design spec's two sections disagreed on layout; the alternative left two elements both claiming the row's `border-t`. Replacing the whole row is cleaner.

Also chosen because unspecified: the submit label "Add unit", both field placeholders, and "Loading build units…".

#### Defect Found and Fixed

**The defect:** After a refused rename (409), the error message did not clear on Cancel, on Escape, on collapsing and re-expanding the row, or on re-opening the rename form. It persisted until a successful save. The implementation had cleared `rowError` at the start of every *attempt* (correct), but nothing cleared it on the paths that *abandon* an attempt.

**The fix** in `components/editor/build/build-unit-row.tsx`:

`rowError` is now cleared in five places:
1. On starting a rename attempt (before the `await`, as before).
2. On successfully saving a rename.
3. On clicking Cancel or pressing Escape to leave rename.
4. On toggling the row closed (collapsing it).
5. On toggling the row open (expanding it).

The last two points are subtle because the list is an accordion — opening a *different* row collapses this one without this row's handler running, and a row can be collapsed mid-flight while a mutation awaits, leaving `setRowError` to fire on a closed row. Deliberately **not** cleared on typing in the rename input — the user continues the interaction rather than abandoning it, the refused title stays on screen, and the next submit clears it anyway.

#### One harness bug, found on the first run and fixed

The very first run died in setup before reaching a single assertion:

```
Clerk Backend API POST /sessions/sess_.../tokens answered 415 Unsupported Media Type
```

`clerkRequest` in `scripts/verify-build-units-http.ts` set `Content-Type: application/json` only when a body was present, and minting a session token is a bodyless POST. `@clerk/backend` sets that header unconditionally on every non-multipart request regardless of body (`node_modules/@clerk/backend/dist/chunk-SYH6K6S7.mjs:5712`), which is why the app's own Clerk calls never hit this. The header is now sent on every request, with a comment recording why so a later "only send it when there's a body" tidy-up does not reintroduce the 415.

**This was a bug in the harness, not in the app.** Worth stating plainly: the app code under test was never at fault here, and no application file was touched by this pass.

#### `concurrent` — item 3 closed, at the HTTP layer

All five assertions passed against a running dev server, authenticating as the owner over `Authorization: Bearer <jwt>` (the script confirmed the transport with a `GET /api/projects` → 200 before starting).

- All 8 concurrent `POST`s answered 201.
- The 8 returned sequence numbers were distinct, and arrived **out of order** — `[5, 8, 2, 7, 4, 1, 3, 6]`. The interleaving is the evidence: it shows the requests genuinely overlapped rather than queueing, and still collided on nothing.
- The sequence set was contiguous `1..8` with no gaps.
- `nextBuildUnitSequence` went 1 → 9, delta exactly 8 — no number burned, none reused.
- A follow-up `GET` listed exactly 8 persisted units in sequence order.

Unit 38 had proven this at the database layer with a direct `tsx` script; what was missing was the same guarantee **through the route**, with the guard, body parsing, and response mapping in the path. That gap is now closed.

#### `cross-project` — item 2 closed for the row-scoping half

Four assertions passed, one skipped.

- Control: a legitimate `PATCH` of a project's own unit through its own path → `200`, `unit.status = "in progress"`. This is the assertion that makes the rest mean anything — without it the 404s below would be equally consistent with "PATCH is simply broken."
- `PATCH` of B's unit id through A's path → `404 {"error":"Not found"}`.
- `DELETE` of B's unit id through A's path → `404 {"error":"Not found"}`.
- B's row was byte-identical afterwards, **`updatedAt` included** — so a silent write landing identical values would have been caught, not just a write that changed something visible.

The skip is the mirror case: a genuine non-member hitting B's own path. It needs `VERIFY_COLLABORATOR_EMAIL` and a second Clerk account. Without one, every caller in the run is a member of both projects, so only the row-scoping half of the isolation guarantee is exercised — the membership half is untouched.
