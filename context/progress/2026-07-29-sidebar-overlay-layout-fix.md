# Sidebar-overlay layout fix

_2026-07-29 — not spec-driven._

- **Sidebar-overlay bug fixed on Home, Discovery, and Specs.** User-reported: the floating project sidebar (`fixed`, `w-80`, `z-30`) covered Discovery's centered form — its Back button and question fields sat under the sidebar with no indication anything was hidden. Root cause: `--canvas-inset-left` (set by `EditorRoomShell` from the sidebar's open state) was only ever consumed by Canvas's floating chrome (`canvas-controls.tsx`); the other three routes' root content never read it, so it did nothing for them. Canvas is deliberately kept **literally** full-bleed (`ui-context.md`'s existing rule) so the fix could not just add `padding-left` to the shared wrapper in `editor-room-shell.tsx` — that would double-offset Canvas's already-compensating floating controls. Instead, each of the three affected routes' own root element now carries `pl-(--canvas-inset-left,0px) transition-[padding-left] duration-200 ease-out` (matching the sidebar's own transition timing): `discovery-view.tsx`'s outer wrapper, `specs-view.tsx`'s outer wrapper (its own left rail was flush against the edge, same bug), and a new thin wrapper div around `project-home-view.tsx`'s existing `mx-auto`-centered content (needed because that div's own `mx-auto` centering can't be the same element consuming the padding — padding-left on a centered box just insets its content, it doesn't shift the box). `ui-context.md`'s Layout Patterns and Layout Tokens sections updated to document the split: Canvas stays full-bleed with only floating chrome clearing the sidebar; Home/Discovery/Specs shift their content instead, since their controls are in document flow rather than floating. `tsc --noEmit` and `eslint` both clean on the four touched files. **Not independently browser-verified this pass** — reasoned from the same `--canvas-inset-left` mechanism already proven correct for Canvas's floating controls, but not re-driven in a live signed-in session.
