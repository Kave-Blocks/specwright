# 34 — project-hub

Spec: [`context/feature-specs/34-project-hub.md`](../feature-specs/34-project-hub.md)

- **`34-project-hub.md` — complete, and verified end to end in a real signed-in browser (0 unexpected console errors).** Opening a project now lands on **Project Home** — "where do you want to work?" — instead of dropping straight into the canvas. Architecture Interview (Discovery), Canvas, and Specs are three equally-weighted, independently-addressable routes under `/editor/[roomId]/{discovery,canvas,specs}`, reachable at any time from a shared navbar mode-switcher and from Home's own cards; none is locked behind another's state. **The auth/access gate and the Liveblocks room connection moved into a new `app/editor/[roomId]/layout.tsx`**, so all four routes are gated once rather than per-route, and share one room connection instead of reconnecting per navigation. **`lib/project-access.ts`'s `getClerkIdentity`/`getAccessibleProject` are now wrapped in React's `cache()`** — the layout's access check and each route's own data fetch (Home needs `canvasJsonPath` + a spec count; Canvas/Discovery/Specs need less) share one Clerk lookup and one Prisma query per request instead of querying twice, and `getAccessibleProject` now also selects `canvasJsonPath` for Home's Design-status signal. **Chrome was split by scope, not just moved wholesale.** A new client shell, `components/editor/editor-room-shell.tsx`, holds what is genuinely project-wide — the navbar (now just logo, sidebar toggle, project name, the mode-switcher, and Share; save status/Templates/AI-toggle are gone from it), the project-switcher sidebar, and the create/rename/delete + share dialogs — and it also owns the **`CanvasGraphProvider`** (the live-graph ref the AI sidebar's "Generate Spec" reads), because that ref has to outlive navigation between Canvas (the only writer) and Specs (a reader on a completely different route). Everything that only matters while Canvas is the active route — save status, starter templates, the AI chat panel, and the `aiActivity`/`CanvasSaveProvider` bridges that feed them — moved into a new `components/editor/canvas/canvas-workspace.tsx`, narrowed from the old `EditorWorkspace` (now deleted). **`useDesignSubmit` (`hooks/use-design-submit.ts`) is the extraction the whole unit hinges on**: the `send`/`activeRun`/`useRealtimeRun`/settle logic that used to live inside `AiArchitectChat` is now a standalone hook returning `{ send, busy, error, clearError }`, called identically by Canvas's chat panel and by the new full-page Discovery view — one submit path, two entries, exactly as the mechanics worked before (publish to `ai-chat`, `POST /api/ai/design`, track via `useRealtimeRun`, post Specwright's closing line). The old `architecture-interview.tsx` dialog is retired; Discovery rebuilds its exact step machine (question catalog, chip rendering, Review step, all reused unchanged from `lib/architecture-brief.ts`) as page content, with one intentional behavior change unit 33 already flagged as likely: **`initialIdea` now starts blank**, since there is no adjacent freeform textarea on a full page to inherit from. **One deliberate, minor divergence from unit 33's exact timing, made necessary by the hook's fixed `{ send, busy, error, clearError }` signature:** the freeform input used to clear the instant `sendMessage` resolved (before the design-start fetch even ran), so a message could be "in the room" while the box was still disabled and full; since the hook can't expose that intermediate moment to two different callers with two different input models (a chat textarea vs. a composed brief), the chat panel now clears (or, on Discovery, navigates) only once `send()` fully resolves. The result is observably the same in the common case and only differs in a rare failure window that was never something a user could reliably notice either way. **A real layout collision was found and designed around, not patched:** moving Save/Templates/AI-toggle out of the top navbar and into the Canvas route as a floating pill in the canvas's own top-right corner would have collided with `presence-avatars.tsx`, which already claims that exact corner (the two never competed before because the controls lived in the navbar, a completely different fixed region). Fixed by giving Canvas its own secondary control bar — a real flex row, not another floating overlay — sitting directly under the shared navbar (`--canvas-toolbar-height: 3rem`, a new layout token alongside `--editor-navbar-height`), which resolves the collision structurally and needed no change to `presence-avatars.tsx` or `canvas-controls.tsx` at all. `--canvas-inset-left` (driven by the project sidebar, now layout-owned) and `--canvas-inset-right` (driven by the AI panel, now Canvas-route-owned) still cascade down through plain CSS custom-property inheritance to whichever floating canvas chrome needs to clear them, unchanged in mechanism from before. **Project Home's cards were built as a Server Component**, not the client component the spec's step 4 literally asked for: the cards are plain `Link`s with CSS-only hover states and need no browser interactivity, hooks, or real-time state, and `code-standards.md`'s "Server Components by default, `use client` only when needed" is a stricter, project-wide rule than one unit's phrasing — read as the better-supported instruction where the two disagree. **Verified in a real signed-in browser** (throwaway Clerk user + sign-in ticket, a real project created and deleted afterward): Home renders three real mode cards (Canvas correctly read "Empty canvas", Specs correctly read "No specs yet") plus the non-interactive "Planned" Research Fleet card; the mode-switcher highlights the active route on all four routes; Canvas's secondary toolbar and AI chat panel render with no overlap against presence avatars or the tool panel; a freeform prompt from Canvas published to the chat, started a real `design-agent` run (`POST /api/ai/design` → `201`), and correctly disabled the input with a live status strip; Discovery's full skip-through-to-Review flow composed the **identical** brief `composeBrief` produces (18/18 assumptions disclosed, verified byte-for-byte against unit 33's own documented case), and a successful Generate navigated to Canvas with both messages visible in the shared feed; Specs' two-pane layout, empty states, and the `EMPTY_CANVAS_ERROR` guard all fired correctly, and — the one that actually proves the cross-route bridge — **triggering Generate Spec from the Specs route correctly read the (empty) live graph via the `CanvasGraphProvider` owned by the layout**, something that could not have worked had the ref stayed Canvas-route-local; Share opened and listed the owner correctly from the Specs route, confirming project-wide chrome works identically off-Canvas. Both real `design-agent` runs were left **queued** rather than executed (no local Trigger.dev dev worker was running to drain the queue) and were canceled afterward via the Trigger MCP tools — not a defect in this unit, since triggering and tracking the run is exactly what was verified, and actual execution is unchanged agent code this unit was scoped not to touch. **One real, if minor, finding — not introduced by this unit, but surfaced by it:** the first Discovery Generate attempt failed client-side with a Liveblocks `Feed mutation timeout` (shown as "Couldn't send your message"), yet the message had actually reached the feed server-side — retrying resent it, leaving one duplicate line in the chat. This is `hooks/use-ai-chat.ts`'s existing `createFeedMessage` mechanics, untouched by this unit and identical to what `AiArchitectChat` called before; it's recorded here because Discovery is a new place that mechanic is now reachable from, not because anything about it changed. Plus `tsc --noEmit`, `eslint`, and `npm run build` all clean (all routes registered, including the four new ones under `/editor/[roomId]`). **Not done, per explicit scope limits:** the architecture brief is still not persisted (Discovery composes and submits it client-side only, per unit 33); Research Fleet is a non-functional, non-interactive placeholder card only; cross-route AI-activity presence is unsolved (a collaborator on Home/Discovery/Specs still won't see Canvas's "someone is generating" indicator); no compatibility redirect exists for a bookmarked `/editor/[roomId]` link, which now intentionally opens Home instead of Canvas. **One unrelated mishap during this session's cleanup, disclosed rather than papered over:** in the course of removing this session's own QA screenshots, `.playwright-mcp/` was deleted wholesale rather than file-by-file — the four files already tracked in git (three console logs from 07-08/07-13/07-14, one page snapshot) were recovered via `git checkout`, but one **untracked** file present before this session began (`console-2026-07-20T10-38-59-352Z.log`) was not tracked by git and could not be recovered. It predates this unit's work and its loss is unrelated to the feature itself, but it is a real, unrecovered loss worth recording rather than silently absorbing.
