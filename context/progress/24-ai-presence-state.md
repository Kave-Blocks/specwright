# 24 — ai-presence-state

Spec: [`context/feature-specs/24-ai-presence-state.md`](../feature-specs/24-ai-presence-state.md)

- `24-ai-presence-state.md` — complete. Shared AI activity indicators so everyone in the room sees when generation is in progress — UI, presence, and realtime status signals only (no generation logic added; `lib/design-agent/{plan,apply}.ts` + `mutateFlow` untouched). **Key architectural change — Liveblocks Feeds replace the `23`-era broadcast channel.** The spec directs "check the installed agent-related features … follow Liveblocks best practices for feeds/presence **instead of creating parallel realtime state** … create or reuse a Liveblocks feed named `ai-status-feed`." `@liveblocks/{client,react,node}@3.22` ship a first-class **Feeds** API (`useFeeds`/`useFeedMessages`/`useCreateFeed`/`useCreateFeedMessage`; node `getFeed`/`createFeed`/`createFeedMessage`; `FeedMessageData`/`FeedMetadata` as extendable global types), so the `23` `broadcastEvent`/`RoomEvent{type:"ai-status"}` mechanism **was** the "parallel realtime state" the spec warns against and is now **removed**: `RoomEvent` reverts to `Record<string,never>` and status flows through the shared `ai-status-feed` feed. **Schema (item 3)** new **`types/tasks.ts`** — `AI_STATUS_FEED_ID = "ai-status-feed"`, `AiStatusPhase`, and the feed payload **`AiStatusFeedMessage = { text?: string; phase?: AiStatusPhase }`** (a `type`, not `interface`, so it satisfies Liveblocks' `Json` constraint; **`text` optional** per spec, kept generic for design *and* future spec generation), plus **`parseAiStatusFeedMessage(unknown)`** which validates a plain object (rejects `null`/arrays/non-objects, checks optional `text` is a string and `phase` is a known phase) → returns a clean message or `null`. `liveblocks.config.ts` sets `FeedMessageData: AiStatusFeedMessage` (imported via `import type`) + `FeedMetadata: Record<string,never>`. **Producer** `trigger/design-agent.ts` — `announce()` now writes `liveblocks.createFeedMessage({ roomId, feedId: AI_STATUS_FEED_ID, data:{ phase, text } })` (was `broadcastEvent`) and is **best-effort** (try/catch + `logger.warn`, never throws) since status is non-critical — so the error-path's redundant nested try/catch collapsed. `ensureAiStatusFeed()` (new **`lib/liveblocks.ts`** helper: `getFeed` → on miss `createFeed`, idempotent, both catch) runs at task start before the first publish. **`app/api/liveblocks-auth/route.ts`** also calls `ensureAiStatusFeed` after `ensureRoom` (best-effort, wrapped so it can never block a room join) so subscribers never hit a missing feed before the first generation. Feed read/write is covered by the existing `session.FULL_ACCESS` (`*:write` → all features incl. `feeds:write`). **Consumer hook** new **`hooks/use-ai-status.ts`** `useAiStatus()` → `{ message, isWorking }`: reads the **non-suspense** `useFeedMessages(AI_STATUS_FEED_ID)` from `@liveblocks/react` (on purpose — the suspense variant would re-suspend the canvas inside `ClientSideSuspense`, and a missing feed degrades to "no status" instead of throwing to the error boundary), picks the **most recent** message by `createdAt`, and **validates** it through `parseAiStatusFeedMessage`; `isWorking = useOthers().some(o => o.presence.thinking)` (presence, so it self-heals via TTL if a worker dies — the feed's last message would otherwise linger). Returns memoized refs so it can drive an effect without cascading. **Sidebar thinking state (item 1)** — the sidebar renders **outside** the `RoomProvider` (a flex sibling of the canvas), so shared state is bridged out via the **`CanvasSaveProvider` pattern**: new **`components/editor/ai/ai-activity-context.ts`** (`AiActivity{ isWorking, status }`, `IDLE_AI_ACTIVITY`, `AiActivityControlsProvider`/`useAiActivityControls` exposing `setActivity`), a null-rendering **`components/editor/canvas/ai-activity-bridge.tsx`** inside `CanvasFlow` that pushes `useAiStatus()` up through `setActivity` (stable deps → one update per real change, no loop — mirrors the save-status bridge), `EditorWorkspace` owns `aiActivity` state + memoized controls and threads `aiActivity` → `AiSidebar` → `AiArchitectTab`. In `AiArchitectTab`, **`busy = pending || aiActivity.isWorking`** (a collaborator's generation also locks the input): a small spinner+status bar shows the latest feed `text` (fallback "Specwright is working…"), the `Textarea` is **disabled**, the send button swaps `Send` → spinning `Loader2` and disables, and the starter chips disable — but the header/tabs/scroll/close stay usable (**whole sidebar never dimmed/blocked**, per scope). **Feed banner** `components/editor/canvas/ai-status-feed.tsx` rewired from `useEventListener` → `useAiStatus()`: still a top-center canvas banner visible to everyone (even with the sidebar closed), **presence-driven visibility** (show while `isWorking`, linger the final message 4s, then hide) so a persisted terminal message never **flashes stale on page load** (when nothing is working); both setState calls are deferred into `setTimeout`s to satisfy `react-hooks/set-state-in-effect`. **Thinking cursors (item 4)** `components/editor/canvas/cursor.tsx` — the badge's pulsing dot became a **small spinner** (`Loader2` `size-3 animate-spin`, inherits the badge's `var(--bg-base)` text color) shown only when `thinking` (already fed `other.presence.thinking` by `LiveCursors` from `19`; humans are always `thinking:false`). **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean (all routes registered), plus a 15-assertion unit test of `parseAiStatusFeedMessage` (valid text/phase/empty/extra-keys/all-4-phases; invalid null/undefined/string/number/array/bad-text-type/bad-phase → `null`) — all pass. Confirmed against the pinned `@liveblocks/{react,node}@3.22` type defs that the Feeds hooks/methods exist, `FeedMessageData` is the extendable global for message payloads, `FULL_ACCESS = ["*:write"]` grants `feeds:write`, and non-suspense `useFeedMessages`/`useOthers` from `@liveblocks/react` share the same `RoomProvider` context as the suspense hooks. **Not exercised live end-to-end:** the real subscribe→feed-message→sidebar/banner round-trip needs the Trigger.dev dev worker publishing + a signed-in browser (editor is behind the Clerk auth wall, no creds this session — same constraint as `10`–`23`); Feeds may also need enabling on the Liveblocks project (every read/write path is best-effort/graceful, so absence degrades to "no status" rather than breaking). Paths verified via types/build/lint + the validator unit test + API tracing, not a live signed-in run.
