# 25 — sidebar-chat-feed

Spec: [`context/feature-specs/25-sidebar-chat-feed.md`](../feature-specs/25-sidebar-chat-feed.md)

- `25-sidebar-chat-feed.md` — complete. Real-time room chat in the AI sidebar, on a **separate** Liveblocks feed (`ai-chat`) from `ai-status-feed` — chat messages and AI progress never share a feed. **Feed (item 1)** `types/tasks.ts` gains `AI_CHAT_FEED_ID = "ai-chat"`; `lib/liveblocks.ts` generalized its create-or-reuse helper into a private `ensureFeed(client, roomId, feedId)` with two thin exports, `ensureAiStatusFeed` (unchanged behavior, `trigger/design-agent.ts` untouched) and the new `ensureAiChatFeed`; `app/api/liveblocks-auth/route.ts` now ensures **both** feeds in one best-effort `Promise.all` after `ensureRoom`, so a client can subscribe to `ai-chat` before anyone has sent a message. Room-scoped and covered by the existing `session.FULL_ACCESS` (`*:write` → `feeds:write`), so no auth change. **Schema (item 4)** — **`zod` was installed as a direct dependency** (`^4.4.3`; it was already in the lockfile transitively via `ai@7`, but nothing in the project imported it — `23` explicitly noted "zod is not installed" and used `jsonSchema()` instead). `aiChatFeedMessageSchema` = `{ sender: { id, name }, role: "user" | "assistant", content: 1–2000 chars, timestamp: non-negative int ms }`, with `AiChatFeedMessage` **inferred** from the schema (`z.infer`) so type and validator can't drift — and, being an inferred object type rather than an `interface`, it still satisfies Liveblocks' `Json` constraint. `parseAiChatFeedMessage(unknown)` wraps `safeParse` → clean message (unknown keys stripped) or `null`; every feed payload is validated **before rendering**, since it crosses the network from other clients. A Liveblocks feed message carries only `id`/`createdAt`/`updatedAt`/`data` (**no author**), which is why `sender` travels inside the payload. `role` is `"user"` for everything written today; `"assistant"` exists for future AI replies (none are produced — scope limit). `liveblocks.config.ts`'s `FeedMessageData` is app-wide (one type for **all** feeds), so it became the **union** `AiStatusFeedMessage | AiChatFeedMessage`; the feeds stay separate because each reader validates the payload it expects and skips the rest (verified: a chat payload through `parseAiStatusFeedMessage` yields `{}` → no `text` → the status UI renders nothing). **Room boundary change (the enabling refactor)** — the AI sidebar rendered **outside** the `RoomProvider` (which lived in `canvas-room.tsx`), which is why `24` had to bridge status out through `AiActivityBridge`. Chat is read/write, so proxying it through the canvas would have meant bridging a send function back in; instead the providers were **lifted**: new **`components/editor/editor-room.tsx`** (`EditorRoom` = `LiveblocksProvider` + `RoomProvider`) now wraps the whole workspace row in `EditorWorkspace`, so the canvas *and* the sidebar share **one** room connection and the sidebar subscribes to `ai-chat` directly. `canvas-room.tsx` → **`canvas-surface.tsx`** (`CanvasSurface`, git-mv'd) keeps only the error boundary + `ClientSideSuspense` + `Canvas`; its name no longer implies it owns the room. The `24` bridge (`AiActivityBridge` in `CanvasFlow` → `aiActivity` prop) is left as-is — it still works and rewiring it is out of scope, though the sidebar could now call `useAiStatus()` directly. **Consumer hook** new **`hooks/use-ai-chat.ts`** `useAiChat()` → `{ messages, isLoading, selfId, sendMessage }`: **non-suspense** `useFeedMessages(AI_CHAT_FEED_ID)` (same reasoning as `useAiStatus` — chat must not suspend the sidebar, and an unreachable feed degrades to an empty conversation), sorted by the feed's **server-assigned `createdAt`** (not the payload `timestamp`, which is the sender's clock and could be skewed; the payload timestamp is only *displayed*) with an id tiebreak, then validated through `parseAiChatFeedMessage` (malformed → dropped). `sendMessage` builds `{ sender: { id: self.id, name: self.info.name || "Anonymous" }, role: "user", content: trimmed+clamped, timestamp: Date.now() }` from `useSelf()` and writes via `useCreateFeedMessage()`; `selfId` (`null` until connected) both gates sending and identifies own messages. **Sidebar UI (items 2–3)** `AiArchitectTab` no longer keeps chat in local `useState` — the message list **is** the `ai-chat` feed, so every participant sees the same conversation. Bubbles now split on **mine vs. a collaborator's** (not user-vs-AI): each shows sender ("You" for own), a `toLocaleTimeString` timestamp, and the content; own messages are right-aligned with the existing brand-tinted treatment, others left-aligned in `bg-elevated`. The **existing input + send button** are reused: send publishes to the feed, **clears the input only on a successful write**, and then still POSTs `/api/ai/design` (the `23` design trigger is untouched — the scope limit is "don't add backend AI triggering", not "remove what shipped"). A small inline `AlertCircle` error line above the input covers both failure modes (`SEND_ERROR_MESSAGE` / `DESIGN_ERROR_MESSAGE`), replacing the old fake "assistant" bubbles. **The canned `GENERATING_MESSAGE` acknowledgement bubble was deliberately dropped**: publishing it into `ai-chat` would be a status message in the chat feed (explicitly forbidden), and `24` already surfaces exactly that through the sidebar's busy bar + the canvas status banner. `busy = pending || aiActivity.isWorking` still gates the input (unchanged from `24`), so chat sends are blocked while a generation is in flight — existing product behavior, not changed here. **Verified:** `tsc --noEmit`, `npm run lint`, `npm run build` all clean (all routes registered), plus a 27-assertion unit test of `parseAiChatFeedMessage` (valid user/assistant payloads, unknown-key stripping, the 2000-char boundary; `null` for non-objects/arrays/missing or malformed sender/bad role/empty or over-long content/negative + fractional + non-numeric timestamp) **including cross-feed isolation** in both directions — all pass. **Not exercised live end-to-end:** the real two-browser subscribe → send → render round-trip needs a signed-in session (editor is behind the Clerk auth wall, no creds this session — same constraint as `10`–`24`) and Feeds enabled on the Liveblocks project; every read/write path is best-effort or degrades gracefully.
