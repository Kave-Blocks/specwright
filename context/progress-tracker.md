- **Marquee QA follow-up — a real multi-pointer bug found by code review, reproduced on a real touchscreen, and fixed; the reported fix was necessary but not sufficient.** CodeRabbit flagged that `useCanvasMarquee` (`hooks/use-canvas-marquee.ts`) checks `event.isPrimary` only at the *press*, while the `pointermove`/`pointerup`/`pointercancel` listeners it binds on `window` accept events from **any** pointer — so a second contact's moves feed `handleMove` as though they were the first one's, and its release ends a drag still under way. The diagnosis is correct, and **it is reachable through an ordinary gesture rather than an exotic one**: under `select`, `panOnDrag` is off, so a one-finger drag on empty canvas is *ours*; `zoomOnPinch` is on by default; and the first finger of a **pinch-zoom** therefore always lands on the pane and arms a marquee before the second finger arrives. **Reproduced** (real multi-touch through CDP `Input.dispatchTouchEvent` + `Emulation.setTouchEmulationEnabled`, in the live signed-in app, against the pre-fix code): finger 1 pressed empty canvas and barely moved — no rectangle, nothing selected — then finger 2 landed and swept across the shapes, and **a marquee rectangle appeared and a shape was selected**, entirely from finger 2's coordinates, on a gesture finger 1 never made; the selection **survived both fingers lifting**. So a pinch-zoom silently changed the selection. **The prescribed fix — filter the listeners by `pointerId` — is necessary but does not finish the job**, and applying only it would have left a subtler version of the same bug: the foreign pointer stops corrupting the rectangle, but **finger 1 keeps drawing a marquee straight through the pinch**, so the zoom still ends in a spurious selection. A second pointer landing mid-gesture *means the gesture was never a marquee*, so it now **abandons** the marquee outright (via the existing `cancelMarquee`, which restores the selection it started from) rather than merely being ignored. Both halves live in the gesture: `Gesture` carries the `pointerId` that started it, `handleMove` and the `pointerup`/`pointercancel` handler answer to that id alone, and the existing `window` `pointerdown` capture listener — which already spent the click guard — now also cancels on a foreign pointer. That listener runs on `window` in the **capture** phase, *ahead of* the React handler that arms a gesture, so the press that starts a marquee finds `gesture.current` still `null` and **cannot cancel itself** — load-bearing ordering, and the reason the cancel could be folded into the listener that was already there instead of adding a second one. **No desktop behavior changes**: a mouse keeps one constant `pointerId`, so every guard added here is a no-op for it. **Verified:** the *identical* touch script that selected a shape before the fix now leaves the selection completely untouched (no rectangle, 0 selected, throughout and after), while a genuine **one-finger** marquee still draws and selects normally; plus all 12 of `31`'s desktop marquee behaviors re-driven with a real mouse (rect drawn, both shapes selected, click-to-clear, prior selection staying lit through an additive **shift-marquee**, and `Esc` mid-drag restoring the prior selection without its release re-clearing it). `tsc --noEmit`, `npm run lint`, and `npm run build` all clean.

- **`32-hand-tool.md` — complete, and verified end to end in a real signed-in browser (0 console errors). Panning is now its own tool, and hold-space reaches it from anywhere.** Most of item 1 was already true from `30`/`31` and got a *confirmation* rather than an implementation: under `hand` the nodes are `pointer-events: none` (React Flow's `hasPointerEvents` rule, since nothing is selectable or draggable), so a drag on top of a shape already panned; `elementsSelectable={false}` already kept the selection alive-but-inert; and `useCanvasDeleteKeys(_, isSelectTool)` already silenced Delete. **The one behavior genuinely missing was the connector — and getting it took two fixes, the first of which silently did nothing.** `nodesConnectable={!isHandTool}` on `<ReactFlow>` looked like the whole job and *was not*: in the live browser the handle still carried `connectionindicator` and its crosshair, with `nodesConnectable: false` sitting right there in the store. **React Flow's `Handle` never reads the store.** `NodeWrapper` resolves connectability per node (`node.connectable || (nodesConnectable && node.connectable === undefined)`) and hands it to the *custom node component* as an `isConnectable` prop — but `HandleComponent` signs itself `isConnectable = true` **as a parameter default**, so a handle left to itself stays connectable no matter what the flow says. `CanvasNodeRenderer` had never forwarded it (the prop was simply unused, which is why **TypeScript could never have caught this** — and why it took the browser to find). The pre-fix behavior was worse than "connectors still work", because two React Flow subsystems disagreed: `ConnectionLineWrapper` **does** read the store (`renderConnection = !!(width && nodesConnectable && inProgress)`), so the connector started **invisibly**, and the handle carries **`nopan`** — which RF's own pan filter honors — so **the pan was blocked too**. A drag off a shape's edge under `hand` did nothing at all: not the connector, not the pan, i.e. the one gesture the hand tool exists for, dead on exactly the pixels the spec calls out. Forwarding `isConnectable` to all four `<Handle>`s fixes it *structurally*: no `connectionindicator` → the handle falls back to React Flow's base `.react-flow__handle { pointer-events: none }` → it stops being a hit target → **the pane becomes the drag target**, so the drag pans, the cursor is the pane's open hand, and no connector starts. Confirmed by hit-testing: the element under a shape's edge is now literally `react-flow__pane`. **This is also why item 3 (cursor) needed no new CSS at all** — the same mechanism that kills the connector hands the cursor to the pane, so `30`'s crosshair rule stays untouched and simply stops matching. Verified *unregressed* under the other tools: `select` and the shape tools keep connectable handles, the crosshair, a live connection line, and a real edge on drop. **Edges were the second thing still answering the pointer under `hand`, and the spec's own wording forced the issue** ("it is simply not editable"; "open hand while `hand` is active"). React Flow marks a non-selectable edge `inactive`, but that only sets `pointer-events: none` on the `<g>` — and `CanvasEdgeRenderer` re-enables pointer events **inline on descendants** (the hit path is `pointerEvents: "stroke"` + `cursor: "pointer"`, the label is `pointerEvents: "all"`), which beats an ancestor's `none`. So under `hand` an edge kept a **pointer cursor**, stayed **double-click editable**, and — because the label carries **`nopan`** — **pressing on a label would have blocked the pan outright**. Both are now gated on the tool through the existing `useActiveCanvasTool()` context (the same lever `31` built for the resizer). The hover flag is handled by **deriving** `active` as `hovered && !isHandTool` rather than resetting state in an effect: a hit path that stops taking pointer events is hit-tested out from under the pointer and never gets its `mouseleave`, and the repo's `react-hooks/set-state-in-effect` rule rejects the effect anyway — the derivation is both lint-clean and the more honest statement (the tool is the authority on its own hover). **Hold-space (item 2) is a real change of `activeTool`, not a panning special case** — which is the whole design. Because the tool *is* `hand` while the key is down, the toolbar's `aria-pressed`, the `data-canvas-tool` cursor, `elementsSelectable`, `nodesDraggable`, `panOnDrag`, `nodesConnectable`, the marquee's arming, and the delete keys **all follow for free**; nothing needed a second code path. It lives in `useCanvasTool`, which already owned the keyboard. **React Flow was already binding space to pan, invisibly, and that had to be taken away from it.** `panActivationKeyCode` **defaults to `'Space'`** and is OR-ed straight into panning (`const panOnDrag = panActivationKeyPressed || _panOnDrag`). Left on it would be a *second, silent owner of space that disagrees with the first*: the spec says space mid-marquee is ignored, and our hook does ignore it — but RF's `useKeyPress` would still have flipped `panOnDrag` on, so the **next** press on empty canvas with space still held would have panned **and** marqueed at once. `panActivationKeyCode={null}` (with `null`, `useKeyPress` binds no listeners at all — checked in the source, not assumed) makes `useCanvasTool` the one owner of space. **The mid-gesture rule is one `dragging` ref, and it is load-bearing rather than merely polite.** Every gesture space must stay out of the way of — marquee, node move, connector, pan — is a primary-button drag, so a single flag fed by window `pointerdown`/`pointerup`/`pointercancel` covers all four without reaching into React Flow for three different in-progress states. It has to exist because **`hand` turns `nodesConnectable` off, and RF only renders the connection line while nodes are connectable** — so taking the hold mid-connector would have *deleted the connector out from under the drag holding it*. Proven in the browser: with space pressed mid-drag the connection line **survives** and the edge still lands. Three failure modes were closed deliberately: a **`dragend`** listener, because a native drag off the tool panel **swallows the `pointerup` entirely** and would otherwise strand the flag on and leave space dead for the rest of the session; a **`blur`** listener, because Cmd+Tab with space down never delivers the `keyup` and would strand the canvas on the hand tool; and an **explicit tool choice while space is held clears the hold**, so releasing the key cannot undo it. The release is **symmetric** with the ignore rule (the spec is silent, and this is the consistent reading): space let go mid-pan **defers** the return until `pointerup`, so the tool is never yanked out from under a drag in flight. `event.code === "Space"` is `preventDefault`ed unconditionally outside a text field — it stops the page scrolling *and* stops the still-focused toolbar button from re-firing its click. **Verified in the live app** (throwaway Clerk user + sign-in ticket + project, all deleted afterwards), driving real mouse and key events over a canvas of two shapes and a labeled edge: under `hand`, dragging empty canvas **and dragging on top of a shape** both pan while the shape stays put; the pane reads `grab` idle, `grabbing` mid-pan (`draggable dragging`), and **`grab` even over a shape and over an edge**; clicking a shape does not change the selection and Delete/Backspace remove nothing; a shape selected *before* the switch is **still selected**; no handle is connectable, a drag off a shape's edge **pans and creates no edge**, and double-clicking an edge **does not open its label editor** while the label still renders. Hold-space: from `select` it pans and returns to `select`; from a **shape tool** it pans, **does not place a shape**, and returns to that same shape tool; the toolbar flips to `hand` and back (`aria-pressed`), and the cursor with it. Mid-gesture: space during a **marquee** leaves the tool on `select`, the rectangle drawing, no pan, and the selection **identical to the same marquee run without space**; space during a **node move** lets the move complete; space during a **connector** leaves the line drawn and the edge is created. Space typed into a node's label **inserts a space and leaves the tool alone** (the label committed and survived a reload). Plus `tsc --noEmit`, `npm run lint`, and `npm run build` all clean. **Not done (deliberately, per scope limits):** scroll/trackpad panning, zoom, and fit are untouched; no zoom-to-selection or space-drag-to-zoom; no momentum, inertia, or animated panning; the viewport is still not persisted.

- **`31-select-tool.md` — complete, and verified end to end in a real signed-in browser (0 console errors).** Selection, move, resize and delete are now the **select tool's** gestures rather than the canvas's, and empty-canvas drag — which used to pan — now draws a **marquee**. **Scoping the gestures (item 1) is four React Flow props, and one of them does more than it looks.** `elementsSelectable={isSelectTool}` and `nodesDraggable={isSelectTool}` turn click-select and move off under every other tool; `useCanvasDeleteKeys` takes a new `enabled` flag so Delete/Backspace go quiet too. **`elementsSelectable` is also what preserves the selection across a tool switch** — React Flow's `resetSelectedElements()` early-returns while nothing is selectable, so a pane click under the hand tool cannot clear what is selected. That is spec 30's "switching tools does not clear the selection" holding *structurally* rather than by a special case. Resizing needed a separate lever, because `NodeResizer` is rendered by the node and keys off `selected` alone: a new **`canvas-tool-context.ts`** publishes the active tool to the renderers inside the flow, and the resizer is withheld (`selected && isSelectTool`) rather than shown-but-dead. **A side effect of `elementsSelectable={false}` that was found in the browser, not reasoned about:** React Flow gives a node `pointer-events: none` when it is neither selectable nor draggable (its `hasPointerEvents` rule), so under another tool the node **body becomes click-through**. This is what makes "clicking a shape does not select it" true, and it is *load-bearing in both directions* — dragging a node body under `hand` now pans instead of moving it (right), and clicking a shape under a shape tool places a new shape on top of it (consistent with "clicking the canvas places that shape"). Spec 30's connector-cursor guarantee and this spec's "connector creation is unaffected" both survive. **(Superseded by `32`, and the reason it held is not the reason assumed here.** `32` requires that `hand` give connectors up, so handles are now non-connectable — and therefore not hit targets at all — under `hand` alone; every other tool is unchanged. See the `32` entry.) **The marquee is hand-rolled (`hooks/use-canvas-marquee.ts`), and React Flow's own `selectionOnDrag` was rejected for a concrete reason, not a stylistic one.** RF's marquee cannot be made additive or cancellable: it calls `resetSelectedElements()` the moment the drag crosses its threshold, and — the decisive part — `getSelectionChanges` writes `selected` **straight into the internal `nodeLookup`** (its own source comments call it "this hack"), which is **the object `NodeWrapper` renders from** (`useStore((s) => s.nodeLookup.get(id))`). The obvious fix — intercepting the `select` changes on their way to Liveblocks — **would not have worked, and this was checked rather than assumed**: `adoptUserNodes` only rebuilds an internal node when the user node's **object identity changes** (`checkEquality`), and Liveblocks' `useStorage` snapshots are **structurally shared**, so a node whose change we dropped keeps its identity and React Flow happily **reuses the mutated internal node** — the baseline would have silently flickered out of the selection mid-drag. - **Spec payload QA follow-up — unbounded node/edge strings bounded, but with a per-field split the reviewer's patch got wrong.** CodeRabbit flagged that `specNodeSchema`/`specEdgeSchema` (`lib/spec-agent/payload.ts`) bound only the *count* of objects (`MAX_NODES = 300`, `MAX_EDGES = 600`) and not the *size* of the strings inside them: `id`, `label`, `shape`, `source`, and `target` were all unbounded, so up to **900 objects each carrying arbitrarily large strings** could be posted, forwarded verbatim into the `generate-spec` prompt (`buildUserPrompt`), and charged as tokens. The finding is **real and worth fixing** — the array caps gave a false impression of boundedness. It reproduced: a 900-object payload of 100k-char labels (**~90 MB of label text**) parsed cleanly and would have gone straight to the model. **But its prescription — "apply the same bounding pattern used for `content` here" (`.max(500)` on every string) — is wrong for `label`, and would have introduced a regression.** `content` can safely *reject* over-length input **only because its producer already guarantees the bound**: `use-ai-chat.ts` does `slice(0, AI_CHAT_MAX_LENGTH)` before writing to the feed, so a real client cannot exceed it. Node labels have **no such guarantee** — they are typed into a plain `<textarea>` with **no `maxlength`** (`canvas-node.tsx`) and stored in Liveblocks — so `.max(500)` + reject would let **one long label on one node hard-400 the entire spec run for an otherwise legitimate canvas**. So each field is bounded by *what produces it*: **ids** (`crypto.randomUUID`, machine-generated — nothing legitimate approaches the cap) are **rejected** over `MAX_ID_LENGTH = 200`; **labels** (human-typed, uncapped at the source) are **truncated** to `MAX_LABEL_LENGTH = 500`, never rejected. **`shape` is bounded by domain, not by length — strictly stronger than the proposed `.max(50)`.** The value is fed to the model as the node's *meaning* (a cylinder **is** a database — the system prompt teaches all six), so an arbitrary 50-char string is not merely large, it is **nonsense the model would try to interpret**, and a plausible prompt-injection surface. ## Architecture Decisions

- shadcn CLI (v4.13.0) defaults to Base UI (`@base-ui/react`) rather than Radix UI as the primitive layer, and to a "Nova" preset (Lucide icons + Geist fonts) — matches this project's existing icon/font choices, so kept the default instead of forcing `--base radix`.
- The dark palette from `ui-context.md` is defined as raw CSS custom properties (`--bg-base`, `--text-primary`, etc.) in `app/globals.css`, then mapped onto shadcn's semantic variables (`--background`, `--card`, `--primary`, ...) so generated `components/ui/*` files stay untouched and still render on-theme.
- `--color-base` was deliberately NOT registered as a `@theme inline` color token: Tailwind's built-in `--text-base` font-size scale key collides with any color named "base", which silently turned every `text-base` (font-size) utility into a text-color rule and made card titles nearly invisible. Fixed by declaring `bg-base` as a standalone `@utility` instead. Keep this in mind before adding more single-word token names — check for collisions with Tailwind's reserved scale keys (`base`, `sm`, `lg`, `xl`, etc.) first.
- `EditorNavbar` and `ProjectSidebar` are controlled components (open/close state lives in a future parent), not self-managing — this keeps them reusable once `08-editor-workspace-shell.md` composes the full editor shell and adds more sidebar/navbar consumers.
- That parent is `components/editor/editor-shell.tsx`, introduced by the editor-home slice of `04-project-dialogs.md`. It is the single `"use client"` boundary for the editor chrome: it holds `isSidebarOpen` and takes `children`, so route pages (`app/editor/page.tsx`, and later `/editor/[roomId]`) stay Server Components and can do server-side data fetching — satisfying invariant 4 (client components only where interactivity requires them). It was deliberately NOT put in an `app/editor/layout.tsx`: `08-editor-workspace-shell.md` gives `/editor/[roomId]` a different navbar (project name, share button, AI sidebar toggle), so a shared layout-level navbar would have to be branched per-route. Sidebar state resets across an `/editor` → `/editor/[roomId]` navigation as a result; if that becomes undesirable, lift it to a layout with a route-aware navbar rather than duplicating the shell.
- `EditorShell` uses `flex flex-1 flex-col` (not `min-h-screen`) because `app/layout.tsx` already sets `html.h-full` + `body.min-h-full flex flex-col`, and `<main>` carries `pt-14` to clear the `fixed` h-14 navbar. No background class is set on the shell — `globals.css`'s base layer already applies `bg-background` (→ `--bg-base`) to `body`.
- `ClerkProvider`'s `appearance.theme` is Clerk's `dark` theme (from `@clerk/ui/themes`), not the `shadcn` theme, even though `components.json` is present — `03-auth.md` explicitly specified "dark theme as base + override variables with app CSS custom properties" rather than the shadcn theme. All Clerk color/typography/radius variables are pointed at this project's existing tokens (`var(--accent-primary)`, `var(--bg-surface)`, `var(--radius-2xl)`, `var(--font-geist-sans)`, ...) so the two approaches converge on the same visual result without pulling in `@clerk/ui/themes/shadcn.css`.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` were added to `.env.local` (they didn't exist before `03-auth.md`) so `proxy.ts` can derive its public-route matcher from env rather than hardcoded path strings, per spec.

- **Multiplayer presence: remote selection added, live cursors audited + tuned** (reported as "I can't tell whether other users' cursors show, and I can't see what another user has selected"). **Live cursors were already implemented and correct** — presence is written on mouse move in `canvas.tsx` (`screenToFlowPosition` → `updateMyPresence({cursor})`, cleared to `null` on `onMouseLeave`) and read in `live-cursors.tsx`, which is mounted as a child of `<ReactFlow>` inside the `RoomProvider`. Cursors are stored in **flow coordinates** and re-projected per viewer with that viewer's own `[translateX, translateY, zoom]`, so they stay anchored to canvas content under independent pan/zoom. No fix was needed; the reporter simply had no way to test it with one mouse. **Remote selection did not exist and was built.** It cannot ride on the synced graph: `@liveblocks/react-flow` hard-codes `selected: false` in its `NODE_BASE_CONFIG`/`EDGE_BASE_CONFIG`, deliberately keeping selection out of Storage so one user's selection can never clobber another's. Selection therefore travels through **presence**, alongside the cursor: `Presence` gained `selection: { nodes: string[]; edges: string[] } | null` (`liveblocks.config.ts`, `initialPresence` in `editor-room.tsx`, and `selection: null` in the AI agent's `setPresence` so every participant's presence keeps one shape). `canvas.tsx` broadcasts via React Flow's `onSelectionChange`. New `components/editor/canvas/remote-selection-context.tsx` holds **one** presence subscription for the whole flow and exposes `useRemoteNodeSelectors(id)` / `useRemoteEdgeSelectors(id)` through context, so N nodes don't open N subscriptions; `canvas-node.tsx` draws a bounding box + name tag in the selector's presence color (a box, not a shape trace, so it reads the same on diamonds/circles and matches the resizer's box) and `canvas-edge.tsx` takes over the edge stroke color, thickens it, and renders a matching name badge through `EdgeLabelRenderer` at the path midpoint, lifted clear of the edge's own label pill (a remote selection forces that pill to show, so the two would otherwise overlap). Both node and edge badges show `+N` when more than one participant holds the same element. **Presence performance** — three components called a bare, unselected `useOthers()` (`live-cursors.tsx`, `presence-avatars.tsx`, `hooks/use-ai-status.ts`), so every remote *cursor move* (up to 10/sec/person) re-rendered all of them; the repo's own `.agents/skills/liveblocks-best-practices` warns about exactly this. Now: `live-cursors.tsx` uses `useOthersConnectionIds()` + a per-cursor `useOther(id, selector, shallow)`; `presence-avatars.tsx` uses `useOthersMapped` over identity fields only; `use-ai-status.ts` selects straight down to a boolean. `remote-selection-context.tsx` likewise uses `useOthersMapped` with an explicit selection-equality check, so cursor movement never re-renders nodes/edges. **Cursor smoothing vs. pan/zoom** — `cursor.tsx`'s 100ms `transition-transform` smoothed throttled network updates but *also* animated the reposition caused by the local viewport transform, so remote cursors visibly lagged the canvas while panning. Restructured into two layers: `live-cursors.tsx` applies the viewport transform to a wrapper **with no transition** (cursors stay locked to content during pan/zoom), and each `Cursor` translates to its **flow** coordinates inside it with the transition, counter-scaling by `1/zoom` so the pointer and badge keep a constant on-screen size as in Figma. **Testing:** added `scripts/simulate-cursor.ts` (`pnpm simulate:cursor <roomId> [elementId...]`), which injects a phantom participant — moving cursor + held selection — via the node SDK's `setPresence`, the same path the AI agent uses. It reads the room's real node/edge ids out of Storage (`{ flow: { nodes, edges } }`, keyed by id), auto-selects the first node when none is named, and clears presence on Ctrl-C. This makes both features verifiable in a single browser window with one mouse. - **Shape drag-and-drop fixes** (two reported issues: no shape visible while dragging, and the shape jumping away from the cursor on drop): (1) *Invisible drag ghost* — `shape-panel.tsx` handed `setDragImage` an element parked at `left:-9999px`; browsers can only rasterize a drag image from an element painted **within the viewport**, so an off-screen element yields a blank ghost. Fixed by cloning the matching off-screen preview into `document.body` on `dragStart`, positioning the clone `fixed` at the cursor (`clientX/Y − size/2`, so it coincides with where the drag image renders → no flash), calling `setDragImage` with the centered `(w/2, h/2)` hotspot, then removing the clone on the next `requestAnimationFrame` (the drag-image snapshot is taken right after the handler returns, before rAF fires, so the element is still present). The off-screen previews remain as clone templates. (2) *Drop offset* — `canvas.tsx` `onDrop` placed the node's **top-left** at the cursor (`createCanvasNode(position)` where `position` = `screenToFlowPosition(cursor)`), but the ghost is centered on the cursor, so the node landed down-and-right of the ghost. Fixed by offsetting the flow position by half the node size (`point.x − size.width/2`, `point.y − size.height/2`) so the node's **center** lands at the cursor, matching the centered ghost. The theme CSS vars the cloned ghost relies on (`--bg-base`, `--border-default`, `--accent-primary`) are defined on `:root` in `globals.css`, so the body-level clone renders on-theme. Verified with `tsc --noEmit` and `eslint` (both clean); the native drag-image visibility is best confirmed by a manual drag in-browser (a native OS/compositor artifact, not observable in the DOM), while the centered-drop math is deterministic.
